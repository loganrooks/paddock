# Lane Common Scaffold

This file is an authoring scaffold for Round 1 lane task specs.

It is not the final prompt to any auditor.

Each actual lane task spec must be standalone and complete, but the shared language below should be carried into each of them so the lanes do not drift into incompatible standards.

## Shared lane purpose

You are handling one bounded part of Round 1 exploratory audit work for the F1 party-platform game mode corpus.

Your job is not to settle the entire portfolio. Your job is to do strong local exploration inside your assigned lane and produce material that the main thread can later synthesize across the whole portfolio.

## Shared anti-goals

Do NOT:
- turn this into a go/no-go pass
- collapse to feasibility-first reasoning
- ask whether "F1 fans" in the abstract will like it
- assume each mode has one true play context
- try to optimize every mode for universal compatibility
- mistake user-origin for proof of quality
- overreward memey virality while ignoring replay loops

## Shared interpretive rules

### 1. Treat entries as possibility families

Current entries are not fixed pitches. They are mode families, variant clusters, or seeds with open directions.

### 2. Context categories are tools, not final truth

Use categories like local couch, sync, async, community, spectator, solo, and hybrid as heuristics.

If a mode exceeds the grid in an interesting way, say so.

### 3. Distinguish context strength from context tension

For your lane, identify:
- where a mode is clearly strong
- where it can balance multiple contexts well
- where variant forks should make different commitments
- where a context fit would feel forced

### 4. Distinguish virality from retention

For your lane, ask:
- what makes this legible, clip-worthy, funny, intense, or surprising?
- what makes the same group want another round or another session?

### 5. User-origin is a signal only

Some ideas were already pressure-tested more directly by the user.
Use that as a clue about conversational depth, not as a shortcut to quality.

## Shared required lenses

Every lane should, in a lane-appropriate way, address:
- what is already here
- possibility expansion
- context profile / tension map
- user situations
- community / online potential
- launch-gap risks
- what the existing categories did not capture

## Shared required sections

Each lane output should contain:

1. `Lane framing`
2. `What is already strong`
3. `What is weak / thin / generic`
4. `Variant forks and possibility expansion`
5. `Context profile / tensions`
6. `Virality vs replayability`
7. `Community / online / spectator potential`
8. `What to park for later research`
9. `What the categories did not capture`
10. `Recommendations for central synthesis`

## Shared output quality bar

Good lane work should:
- produce sharper distinctions, not just more words
- notice real tradeoffs between versions of a mode
- name where a mode is promising but underdeveloped
- name where a mode is funny in concept but not yet a game
- preserve multiple live possibilities when the evidence does not justify collapse
