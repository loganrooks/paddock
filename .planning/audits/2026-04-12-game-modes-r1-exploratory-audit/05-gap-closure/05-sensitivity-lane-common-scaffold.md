# 05 Sensitivity Lane Common Scaffold

## Shared framing

These lanes are doctrine-audit and protection work.

They should consume:

- the control note
- only the dockets assigned to them
- the target planning docs they own

They should not:

- re-run the challenge packets
- invent rival logic from scratch
- choose winners

## Shared classification and launch intent

Treat this lane bundle as:

- `replanning/revision/gap-filling`

Default launch policy:

- `gpt-5.4`
- `high`

## Required output sections

Every sensitivity lane output must explicitly include:

1. `Lane framing`
2. `Docs inspected`
3. `Dockets consumed`
4. `Direct doctrine protections`
5. `Bounded-open anti-hard-coding findings`
6. `Preserve-only seam findings`
7. `Reversal-sensitive findings`
8. `Inquiry-debt protection findings`
9. `Semantic drift findings`
10. `Concrete doc adjustments or carry-forward notes`
11. `What still requires converged synthesis`

## Shared anti-overreach rule

Sensitivity lanes must not:

- choose final rankings
- promote preserve-only seams
- close inquiry debt
- write roadmap commitments into existence

## Shared cross-docket drift checks

Every lane must also test whether the owned docs create semantic drift or hidden conflict across docket boundaries, especially when the same term carries different pressure in different dockets.

Minimum cross-docket checks:

- `challenge`
  - distinguish low-burden share-by-link / challenge pressure from recurring/programmed challenge cadence, challenge-result shells, and paid/supporter challenge access language
- `showcase`, `spectator`, `audience`, `watchable`
  - distinguish low-burden aftermath, bounded audience shells, spectator readability, and stronger audience-right thresholds
- `hosted`, `operator`, `hybrid`
  - distinguish trusted operators, official hosted convenience, provider / partner host, unpromoted private operators, and collective / plural-host seams
- `event`, `featured`, `weekend`
  - distinguish first explicit shell pressure from true event-memory pressure and from mere cadence packaging
- `support`, `premium`, `membership`, `priority`, `reserved`
  - distinguish recognition/support language from service-bearing convenience and from participant-paid access
- `creator`, `partner`, `reviewed`, `unsupported`, `marketplace`
  - distinguish curated contribution identity, preserve-only reviewed-submission seams, unsupported listings, and reversal-sensitive public publishing

If a lane finds that one doc's safe implication would undermine another docket's guardrails, it must say so explicitly rather than harmonizing the terms silently.
