## Semantic drift that matters

`[evidenced:mixed:internal+external-direct]` Drift does exist, and it matters for later sensitivity.

- `event`
  - local drift:
    - `event carry-over`
    - `event-memory surface`
    - `event board / featured-weekend recap`
    - `race-weekend event`
  - why it matters:
    direct external grounding shows that `daily/programmed challenge`, `event`, and `tournament` are not the same thing. GeoGuessr separates invited challenges, Daily Challenge, Events, and Tournaments. Chess.com separates Daily Puzzle from tournaments. Strava separates club activity, event match, and event insights.
  - carry-forward consequence:
    later sensitivity should not let `featured` or `weekend` language silently imply a true event object.

- `memory`
  - local drift:
    the bundle correctly says `room/group/event memory` are distinct, but sometimes translates them back into one generic recap/history idea.
  - why it matters:
    Strava shows club leaderboard history can be intentionally shallow while event insights keep only the latest five events and personal matched-activity trends stay private and owner-only. Different memory layers can be real without sharing one depth or one visibility model.
  - carry-forward consequence:
    `event memory`, `group memory`, and `player mastery history` should not be treated as one persistence decision.

- `cadence`
  - local drift:
    the bundle uses `cadence` for session pacing, editorial rhythm, shared challenge timing, and event schedule.
  - why it matters:
    GeoGuessr Daily Challenge, GeoGuessr weekly tournaments, Chess Daily Puzzle, and Strava weekly streaks are meaningfully different cadence families.
  - carry-forward consequence:
    the chunk can tighten cadence into families without choosing final labels.

- `mastery`
  - local drift:
    the bundle sometimes uses `mastery` to mean the return loop, sometimes the visible surface, and sometimes the first metric.
  - why it matters:
    GeoGuessr medals and badges, Chess stats and Game Review, and Strava matched activities all show that a mastery surface can be longitudinal and player-owned without dictating one metric.
  - carry-forward consequence:
    the `mastery surface family` can close more tightly than the `first mastery metric`.

## Negative-case / failure evidence note

`[evidenced:cited:external-direct]` The direct external sources surfaced several relevant negative cases:

- `challenge/event residue does not automatically count as mastery`
  - GeoGuessr says Explorer medals only count in single-player, not when a map is played as a Challenge.
  - GeoGuessr Events do not affect rank even though top-three players can earn medals.
  - Chess tournament trophies live separately from the Stats page.

- `group memory can exist without deep historical permanence`
  - Strava club leaderboards reset weekly and, beyond `Last Week`, do not store historical leaderboard data.
  - This is a useful caution against assuming that recurring-group memory needs a heavy permanent archive to be real.

- `event proof can stay private and removable`
  - Strava Activity Event Match can attach an event and club to an activity even when the activity is `Only You`, and the user can remove the match.
  - This is a caution against assuming event memory requires public exposure or irreversible persistence.

- `programmed cadence creates expectation debt`
  - Chess Daily Puzzle resets daily at midnight Pacific Time and supports revisiting past puzzles.
  - GeoGuessr Tournaments are scheduled every Wednesday at a fixed time.
  - Strava Streaks require weekly activity.
  - These are not just names; they are concrete expectation-setting schedules.

`[assumed:reasoned:internal]` The useful negative conclusion is not `avoid these layers`. It is `name them precisely enough that the product does not accidentally promise the wrong kind of continuity, visibility, or staffing burden`.

| Alternative | What it makes concrete | Strongest direct grounding | Main weakness | Current judgment |
| --- | --- | --- | --- | --- |
| `room recap / rematch residue` | session-level memory and immediate social residue | local doctrine plus the absence of heavy group/event memory in room-first references | too thin to carry the whole product-controlled return story | required base residue, not sufficient alone |
| `player-owned mastery history` | longitudinal player history, review, progress, and optional achievements | GeoGuessr medals + badges; Chess stats + Game Review + archive; Strava matched activities | can drift into grind or generic progression if it loses reveal/review texture | strongest first explicit memory surface |
| `recurring-group residue` | lightweight group identity, comparison, and recurring context | Strava clubs, private-group visibility rules, weekly leaderboard reset | easy to overbuild into a social platform or underbuild into invisible folklore | real later-or-parallel layer, but can stay shallow early |

## Findings

### 1. `Event memory` can now be tightened into an `event object threshold`, not a UI guess

`[evidenced:cited:external-direct]` The direct external pattern is consistent:

- GeoGuessr Events are custom maps/settings for a specific time frame, separate from rank, with top-three medals.
- GeoGuessr Tournaments are scheduled weekly, tiered by ELO, and award trophies.
- Chess.com exposes upcoming, joined, completed, and hosted Daily tournaments separately from stats, and separately shows tournament trophies.
- Strava Activity Event Match links an activity to an event and club when time/location conditions are met.
- Strava Club Event Insights compares attendance against previous club events and keeps that insight to the latest five events.

`[assumed:reasoned:internal]` The chunk can now tighten `event memory` to mean:

- there is a distinct event object
- it has a bounded time frame or schedule
- it has event-scoped participation or eligibility
- it produces event-scoped residue such as results, trophies, proof, or comparative event insight

`[assumed:reasoned:internal]` Without those ingredients, the safer translation is `recap`, `featured challenge`, or `editorial pulse`, not `event memory`.

`[open:reasoned:internal]` This does not close:

- which event shell arrives first
- how visible that residue should be
- whether the first explicit Prix surface is a weekend board, hosted-night recap, featured challenge result, or something narrower

### 2. `Cadence` should be carried forward as families, not one taxonomy

`[evidenced:cited:external-direct]` The direct external sources expose at least four distinct cadence types:

- `session pacing`
  - local to the active playable loop and already part of `GAME-04`
- `behavioral consistency cadence`
  - Strava weekly streaks
  - Chess.com daily streak counter based on play/learn activity
- `editorial/programmed cadence`
  - GeoGuessr Daily Challenge
  - Chess Daily Puzzle
- `event cadence`
  - GeoGuessr weekly tournaments
  - GeoGuessr time-boxed Events
  - Chess live/daily tournaments

`[assumed:reasoned:internal]` This is enough to tighten the family split without choosing final names:

- `session pacing`
- `behavioral or mastery continuity cadence`
- `editorial/programmed pulse`
- `event schedule cadence`

`[assumed:reasoned:internal]` The important non-equivalence is:

- an invited friend challenge is a wrapper/use mode
- a daily programmed challenge is a cadence overlay
- a tournament/weekend board is an event schedule only if a real event object exists

`[open:reasoned:internal]` What remains open:

- exact labels such as `daily`, `featured`, `race-weekend`, `weekly`, or `occasional spotlight`
- whether Prix Guesser ever needs a visible `behavioral streak` layer

### 3. `Mastery surface` can close as a family before the first metric does

`[evidenced:cited:external-direct]` The direct external pattern supports a player-owned, longitudinal mastery family:

- GeoGuessr Explorer lets players compete or challenge friends in a country, but medals only count in single-player.
- GeoGuessr Badges reward alternate objectives and are displayed on the profile.
- Chess.com Stats provides time-control and variant breakdowns plus rating history.
- Chess.com Game Review exposes accuracy, key moves, and suggestions to improve.
- Chess.com Archive keeps a searchable history of completed games.
- Strava Matched Activities groups repeated route efforts into a trend over time and keeps them private to the owner.

`[assumed:reasoned:internal]` The chunk can therefore tighten the `mastery surface family` to:

- player-owned history
- review/explanation that turns completed play into future intent
- longitudinal progress/trend visibility
- optional achievement overlays such as badges, trophies, or streaks

`[assumed:reasoned:internal]` This family is tighter than the local bundle had been, but it still does not choose the first metric. The safe carry-forward is `mastery surface family yes, first metric no`.

`[open:reasoned:internal]` Still open:

- first metric
- whether the first visible mastery read is more `progress/completion`, `performance/accuracy`, `collection depth`, or hybrid
- whether any achievement overlay should be public/profile-visible early or remain lightweight/private

### 4. `Group memory` is real, but it does not need to be as deep or as public as event memory

`[evidenced:cited:external-direct]` Strava is especially useful here:

- clubs can be public or invite-only
- non-members cannot see recent activities, discussions, and private group events in invite-only clubs
- club leaderboards reset weekly
- beyond `Last Week`, Strava does not store historical leaderboard data and sends users to profile statistics or training calendar for longer-range history

`[assumed:reasoned:internal]` This gives a useful translation for Prix Guesser:

- `group memory` can be meaningful even if it is shallow, rolling, or recap-oriented
- it does not need to imply public discovery
- it does not need to imply an event object

`[assumed:reasoned:internal]` That means the repo can safely preserve a lighter early answer such as:

- recap/rematch
- recurring-rivalry residue
- last-session or recent-session context

without prematurely implying a deep recurring-group platform layer.

`[open:reasoned:internal]` Still open:

- how much explicit naming beyond recap/rematch is needed early
- whether recurring-group identity deserves a dedicated board/history before other wrapper work closes

### 5. `Daily/programmed challenge` is better translated as a cadence overlay than as proof of event memory

`[evidenced:cited:external-direct]` The direct external evidence separates these more cleanly than the local bundle had:

- GeoGuessr `Play with Friends` and `Only Invited` Challenge are clearly friend challenge/share surfaces.
- GeoGuessr Daily Challenge is a shared daily competition.
- GeoGuessr Events and Tournaments are separate eventized surfaces again.
- Chess Daily Puzzle is a daily editorial surface with archive access.
- Chess tournaments are separately tracked event surfaces.

`[assumed:reasoned:internal]` The safest tightening is:

- `friend challenge` belongs first to the challenge/share wrapper family
- `daily/programmed challenge` belongs first to editorial/programmed cadence, even if it happens to reuse challenge-like substrate mechanics
- `event memory` belongs only after a true event object exists

`[open:reasoned:internal]` This remains challengeable because a future `race-weekend challenge` could become a genuine event object if it gains:

- bounded schedule
- event-scoped participant set
- event-specific results or trophy logic
- event-scoped recap worth revisiting

## What got tighter

`[assumed:reasoned:internal]` This chunk tightened the open space in five specific ways:

- `event-memory` now has a usable threshold:
  it requires a real event object plus event-scoped residue, not just vivid recap language
- `cadence` can now be carried forward as four families:
  `session pacing`, `behavioral/mastery continuity`, `editorial/programmed pulse`, and `event schedule`
- `mastery surface family` can close more tightly:
  player-owned history + review/explanation + progress/trend + optional achievement overlay
- `group memory` has a more concrete but still light translation:
  shallow/rolling recurring-group residue can be valid without becoming a full social platform
- `daily/programmed challenge` now has a better provisional home:
  closer to editorial/programmed cadence than to generic event memory

## What remains challengeable

`[open:reasoned:internal]` The following should stay challengeable rather than being flattened into doctrine:

- whether the first visible mastery read should foreground progress, accuracy, collection depth, or a mixed view

## First-value vs later-value

| Surface family | First-value | Later-value | Preserve-without-prioritizing | Why |
| --- | --- | --- | --- | --- |
| `room recap / rematch residue` | high | medium-high | no | immediate session residue and the lightest way to keep room memory real |
| `player mastery history` | very high | very high | no | strongest first explicit memory layer that supports the already-settled review-backed return loop |
| `achievement overlay` | medium | high | yes | useful once mastery exists, but not required to prove the base loop |
| `recurring-group residue` | medium | high | yes | matters for recurring trusted groups, but can stay shallow early |
| `editorial / programmed pulse` | medium | high | no | real reason to check back now, but brings schedule and expectation burden |
| `event object + event memory surface` | low | high in bounded event shells | yes | only valuable once a real event object exists and deserves its own residue |

## Archetype-to-burden translation

| Archetype | First explicit memory surface | First useful cadence family | Main value created | Main new burden | Carry-forward caution |
| --- | --- | --- | --- | --- | --- |
| `couch / recurring private group` | `room recap / rematch`, later light `group residue` | mostly session pacing, maybe occasional programmed spotlight | house memory, rivalry, repeat gathering | privacy/naming cleanup, low-friction recap, not much more | do not let house memory get mislabeled as `event memory` |
| `private online sync` | `player mastery history` plus recap residue | challenge/share timing first, editorial pulse second | keeps absent friends and solo return connected to the same substrate | clearer separation between `live room`, `challenge`, and `history` | do not force a recurring-group platform layer too early |
| `solo ritual` | `player mastery history`, optional achievement overlay | editorial/programmed pulse or behavioral continuity cadence | strongest repeat-return ownership without requiring publicness | risk of grind, streak debt, or over-instrumented progression | do not let mastery drift into generic grind systems |
| `bounded event shell` | `event object + event memory surface` becomes plausible | event cadence first, editorial pulse second | appointment energy, event proof, shared result residue | host authority, legitimacy, moderation, clearer event boundaries | only use `event memory` here once the event object is actually real |

## Trigger conditions

| Later branch | Trigger condition before it should be prioritized |
| --- | --- |
| `heavier recurring-group memory` | recurring private groups revisit recent standings or reveal folklore often enough that recap/rematch no longer carries the whole group-memory burden |
| `achievement overlay` | the player-owned mastery surface already exists and the product needs lightweight public/private shorthand for progress without locking a single metric |
| `editorial / programmed pulse` | the evergreen library is large enough that resurfacing feels like value, and the operator can sustain the cadence honestly |
| `event object + event memory` | there is a bounded event shell with explicit time frame, participant/result boundary, and event-scoped residue that players actually want to revisit |
| `race-weekend eventization` | a weekend surface has more than themed content; it has real enrollment, results, or proof that make it behave like an event instead of a featured challenge |

## Recommended carry-forward

`[assumed:reasoned:internal]` Recommended carry-forward for later residual synthesis and sensitivity:

- treat `event memory` as a later distinct ledger that requires:
  - a true event object
  - event-scoped residue
  - separation from mastery history and room recap
- treat `mastery surface family` as closed enough to preserve:
  - player-owned history
  - review/explanation bridge
  - longitudinal progress/trend
  - optional achievement overlay
  while keeping the first metric open
- treat `cadence` as a family split, not a one-word placeholder:
  - session pacing
  - behavioral/mastery continuity
  - editorial/programmed pulse
  - event schedule
- treat `daily/programmed challenge` provisionally as:
  - editorial/programmed cadence layered on top of a play surface
  - not automatic proof of an event object
- treat `group memory` as allowed to stay shallower than player history or event memory
