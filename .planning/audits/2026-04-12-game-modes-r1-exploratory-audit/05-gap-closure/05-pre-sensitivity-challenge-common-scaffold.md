# 05 Pre-Sensitivity Challenge Common Scaffold

## Shared framing

These challenge packets exist because the residual synthesis is useful as a classification artifact, but still too eager to route the overall job toward sensitivity.

The current issue is not lack of vocabulary. It is that several branches are now framed as:

- stronger defaults
- better provisional homes
- better-bounded unresolveds

without yet being stress-tested hard enough against their strongest rivals.

These packets therefore exist to:

- treat the current stronger-default branches as hypotheses, not conclusions
- identify what is actually carrying those hypotheses
- expose what would falsify, weaken, or materially re-rank them
- determine what may later enter sensitivity as robust doctrine versus only challengeable provisional judgment

## Shared classification and launch intent

Treat this packet bundle as:

- `initial architecture research/planning`

Default launch policy:

- `gpt-5.4`
- `xhigh`

Reason:

- this is still early architecture-setting and non-foreclosure work
- the central risk is not implementation failure, but over-reading partial closure as stable doctrine
- this round is explicitly about adversarial comparison and avoiding misinterpretation

## Shared governing inputs

Every packet must preserve:

- the existing private-first product center
- substrate-plus-wrappers posture
- layered room/group/event memory doctrine
- staged visibility and audience-right distinctions
- the distinction between:
  - `directly sensitivity-ready doctrine`
  - `bounded-open anti-hard-coding`
  - `preserve-only`
  - `reversal-sensitive`
  - `inquiry debt`

These packets are not supposed to erase those categories by force.

## Shared packet rule

Every challenge packet must cite:

- the exact residual synthesis claims it is trying to stress-test
- the exact `RGR-*` families it still bears on
- the exact packet/chunk outputs whose conclusions it is challenging or pressure-testing

If the packet cannot point to a concrete promoted/defaulted/provisional claim, it is too vague.

## Shared epistemic rules

- Treat current stronger defaults as hypotheses.
- Include the strongest rival branch or rival framing, not just a token alternative.
- Distinguish:
  - current hypothesis
  - strongest rival
  - evidence that strengthens the hypothesis
  - evidence that weakens it
  - what remains unresolved after comparison
- Include direct external grounding in the packet itself.
- Include negative-case or counterexample evidence where available.
- If a source is only analogous in one narrow way, say so explicitly.
- If a loaded term changes meaning between residual synthesis and the challenged packet/output, flag that semantic drift explicitly.

## Required sections

Every challenge output must explicitly include:

1. `Challenge framing`
2. `Target hypothesis`
3. `Why this hypothesis matters`
4. `Gap justification`
5. `What is already settled and not being relitigated`
6. `Strongest rival framing(s)`
7. `Path of inquiry`
8. `Direct external source register`
9. `Reference translation`
10. `Negative-case / counterexample note`
11. `Evidence that strengthens the current hypothesis`
12. `Evidence that weakens or complicates it`
13. `Comparative verdict`
14. `What would falsify or materially re-rank the hypothesis`
15. `What remains challengeable`
16. `Sensitivity implications`
17. `What should remain out of sensitivity`
18. `What later converged challenge synthesis must reconcile`

## Shared anti-overreach rule

These packets should not:

- pretend to “disprove” a branch just because it is not the current favorite
- collapse reversal-sensitive or preserve-only branches into dead branches
- turn challenge results into roadmap commitments
- use sensitivity as an excuse to postpone still-load-bearing competitive comparison
