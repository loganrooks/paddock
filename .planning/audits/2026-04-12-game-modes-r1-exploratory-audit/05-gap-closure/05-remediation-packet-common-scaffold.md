# 05 Remediation Packet Common Scaffold

## Shared framing

These packets are not generic audits and not patch-only cleanup.

They exist because the existing `05-gap-closure` bundle:

- improved the project’s conceptual vocabulary
- surfaced real operating-model terrain
- but still over-closed several rankings, orderings, and branch comparisons before enough direct external inquiry had been done

These packets should therefore:

- preserve the useful doctrine already learned
- reopen only the inquiry surfaces that were closed too early
- produce direct external grounding where the register says it is needed
- leave some things explicitly open rather than forcing premature closure

## Shared classification and launch intent

Treat this packet bundle as:

- `initial architecture research/planning`

Default launch policy:

- `gpt-5.4`
- `xhigh`

Reason:

- these packets are still exploratory and canon-sensitive
- they are shaping rerun-input doctrine, not merely checking it
- misclassification, misreading, and over-closure are the central risks

## Shared governing inputs

Every packet must preserve:

- private-first product center
- substrate-plus-wrappers posture
- layered memory and cadence doctrine
- staged visibility and audience-right distinctions
- Round 2B non-foreclosure seams
- archetype-aware thinking established in Round 2A

These are governing inputs, not topics to casually relitigate.

## Shared gap-justification rule

Every packet spec must include a `Gap justification` section that:

- cites the exact `GCO-*` entries it addresses
- says why those IDs belong together in one packet
- says what the packet is not trying to close

If the packet cannot name specific `GCO-*` entries, it is too vague to launch.

## Shared epistemic rules

- Distinguish:
  - inherited doctrine
  - direct external grounding produced in this packet
  - external-traceable background only
  - remaining open judgment
- Do not treat older repo-local syntheses as direct external grounding.
- Include a short `Reference translation` section:
  - what is analogous here
  - what is not analogous
  - what is borrowed as concern versus as solution
- Sample negative-case evidence where relevant:
  - failure modes
  - abandonment
  - burnout
  - operator pain
  - user misread
- Do not convert pattern-family identification into ranking unless the packet actually justifies that ranking.

## Required comparative sections

Every packet output must explicitly include:

1. `Packet framing`
2. `Gap justification`
3. `What is already settled`
4. `Path of inquiry`
5. `Direct external source register`
6. `Reference translation`
7. `Negative-case / failure evidence note`
8. `Live alternatives`
9. `Findings`
10. `First-value vs later-value`
11. `Archetype-to-burden translation`
12. `Trigger conditions`
13. `Recommended carry-forward`
14. `Explicit deferrals`
15. `What should remain open`
16. `What later converged synthesis must reconcile`

## Shared output standard

Packet outputs should be:

- comparative
- explicit about uncertainty
- explicit about what got weaker or stronger after outside research
- careful not to make one polished reference feel canonical

They should not read like:

- generic product essays
- one-sided advocacy for a favorite branch
- pseudo-closure built from internal restatement
