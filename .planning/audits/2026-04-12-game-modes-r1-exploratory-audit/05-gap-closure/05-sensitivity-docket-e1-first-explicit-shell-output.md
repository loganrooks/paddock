# 05 Sensitivity Docket E1: First Explicit Shell Output

## 1. Docket framing

- Mode: `feature-to-doc map`
- Classification: `initial architecture research/planning`
- Purpose: translate the challenge-round event-shell result into doc-level guardrails so the planning canon preserves the current ordering pressure without treating it as closed.
- This docket is about the first explicit shell, not the whole event-memory doctrine.
- It does not choose a final recap UI, permanence policy, cadence taxonomy, or event-memory product surface.

## 2. Target feature pressure

- strongest current first explicit shell: `hosted-night recap / session report`
- strongest current rival: `featured challenge result`
- later true-event-memory seam: `weekend board / scheduled event board`
- the pressure to protect is not just "which surface sounds coolest"; it is whether the docs keep three different claims separate:
  - a post-session shell can become explicit before true event memory exists
  - `featured challenge result` is still a live rival and should not disappear
  - a later `weekend board` may become the strongest true-event-memory shell without being the first explicit shell by default

## 3. Current gate classification

- Primary classification: `bounded-open`
  - `hosted-night recap / session report` is the strongest current first explicit shell, but sensitivity may not treat that as a final winner.
  - `featured challenge result` remains a meaningful rival.
- Direct doctrine boundary:
  - `first explicit shell` and `first true event-memory shell` are not the same question.
  - `event memory` still requires a true event object.
- Preserve-only / later-seam boundary:
  - `weekend board / scheduled event board` remains the strongest later true-event-memory shell, not the default first explicit shell.
- Inquiry debt handed off to `E2`:
  - permanence
  - visibility ladder
  - navigation depth
  - cadence taxonomy
  - mastery/history surfaces

## 4. Current survivor and strongest rival(s)

- Current strongest survivor:
  - `hosted-night recap / session report`
  - The challenge round narrowed the likely first explicit shell toward a bounded post-session object with host/session residue rather than toward a heavier scheduled-event board.
- Strongest rival:
  - `featured challenge result`
  - It stays live because a named challenge-result surface can also become explicit before a true event object exists.
- Important later seam, but not same winner contest:
  - `weekend board / scheduled event board`
  - This remains the strongest current candidate for first true event memory later, once genuine event-object traits exist.
- Surviving doctrinal distinction:
  - `hosted-night recap` answers "what explicit shell might appear first?"
  - `weekend board` answers "what later shell might deserve the name event memory?"
  - `featured challenge result` sits between those pressures and can distort doc wording if it is not named explicitly.

## 5. Why this pressure matters

- `PROJECT.md` already distinguishes `event container`, `room`, `game instance`, and `session wrapper`, then separately keeps memory and cadence layered. That makes the repo vulnerable to wording drift in either direction:
  - over-reading any explicit post-session shell as a true `event container`
  - or under-reading recap/report residue because only true event objects sound "serious"
- `LONG-ARC.md` already protects layered memory, layered cadence, and staged visibility. If the docs use `event`, `featured`, or `showcase` loosely, that doctrine can be silently flattened again.
- `ROADMAP.md` already gives Phase 5 a session-end summary/replay surface and Phase 6 a warning not to flatten replay history, room/group memory, event memory, and content history into one ledger. That combination is useful, but it can also be misread as either:
  - "summary/replay already solved the first shell question"
  - or "nothing explicit should exist until a later event board exists"
- `01-CONTEXT.md` explicitly preserves authored-content identity apart from later session snapshots and event/editorial wrappers, while also refusing to decide event-memory structures in Phase 1. That means the substrate can protect a later recap/report shell, but only if the docs do not prematurely equate recap, challenge result, and event memory.

## 6. Relevant planning surfaces

| Surface | Current pressure point | Why this doc matters for `E1` |
| --- | --- | --- |
| `PROJECT.md` | vocabulary for `event container`, `room`, `game instance`, `session wrapper`; Milestone 2 memory/recurrence; layered memory and cadence posture | It sets the top-level nouns. If those nouns drift, the later sensitivity lanes will inherit the wrong shell ordering. |
| `LONG-ARC.md` | room/wrapper/memory doctrine; staged visibility ladder; protected separation between room shell and event/container layers | It is the main doctrine surface for keeping explicit recap shells, challenge shells, and event-memory shells distinct. |
| `ROADMAP.md` | overview separation between room shell, active game instance, visibility surface, and recurrence; Phase 5 summary/replay; Phase 6 carry-forward memory/cadence constraints | It is the most likely place for the first-shell question to be accidentally closed by implementation-adjacent wording. |
| `01-CONTEXT.md` | future-awareness seam for session snapshots and event/editorial wrappers; explicit non-decision on room/group/event-memory structures | It protects the Phase 1 substrate from prematurely hard-coding a post-session object model. |

## 7. Per-doc implication map

### `PROJECT.md`

- Safe:
  - keep `event container`, `room`, `game instance`, and `session wrapper` distinct
  - preserve layered memory and cadence language
  - allow later wrapper examples to include session recap/report, challenge, and spectator-facing shells without treating one example as resolved order
- Would overcommit:
  - implying that the first explicit shell is already settled because Milestone 2 mentions session history or room/group memory
  - implying that anything called `event` or `featured` already deserves true event-memory treatment
- Would silently foreclose:
  - naming later challenge/share surfaces repeatedly while leaving post-session recap/report implicit
  - or naming only `event container` language in a way that makes recap shells sound unserious or nonexistent
- Must remain explicit:
  - the first explicit shell is not closed
  - `hosted-night recap / session report` is currently strongest
  - `featured challenge result` remains a real rival
  - true `event memory` is still later and separately gated

### `LONG-ARC.md`

- Safe:
  - preserve the doctrine that room shell, active game instance, and event/container layers are distinct
  - keep visibility, memory, and cadence as separate axes
  - let a bounded explicit recap/report shell exist before a true event-memory ledger exists
- Would overcommit:
  - treating the visibility ladder or event/container language as if the first explicit shell must wait for a heavier scheduled-event object
  - treating recap/report residue as if it already proves a settled post-room product surface
- Would silently foreclose:
  - letting `challenge`, `showcase`, or `event` absorb every explicit after-play surface
  - collapsing editorial cadence and event cadence so that any recurring challenge result starts sounding like full event memory
- Must remain explicit:
  - a read-after shell can become explicit before true event memory
  - `featured challenge result` is not identical to `event memory`
  - `weekend board` remains later true-event-memory pressure, not default first-shell proof

### `ROADMAP.md`

- Safe:
  - keep v1 committed to live private rooms and the watchable session loop
  - treat Phase 5 summary/replay as room ritual that preserves a seam toward later recap/report shells
  - keep Phase 6 memory/cadence warnings active so later reruns do not flatten recap, replay, room/group memory, and event memory
- Would overcommit:
  - reading Phase 5 summary/replay as proof that the first explicit shell is already decided and already implemented
  - reading future recurrence or event language as proof that a `weekend board` is the first explicit shell
- Would silently foreclose:
  - hardening Phase 5 closeout into an in-room-only artifact with no outward recap/report seam
  - or skipping recap/report language so thoroughly that only `featured challenge` or later `event` language sounds like a real explicit shell
- Must remain explicit:
  - the roadmap still stops at the private-room wrapper
  - Phase 5 closeout is adjacent to, not identical with, a later recap/report shell
  - no roadmap commitment exists yet for `featured challenge result` or `weekend board`

### `01-CONTEXT.md`

- Safe:
  - preserve stable content identity apart from later session snapshots and event/editorial wrappers
  - keep wrapper reuse and future context records open
  - keep event-memory structures out of Phase 1 decisions
- Would overcommit:
  - adding event-object or recurrence-model assumptions to Phase 1 just because later recap/report or challenge-result shells are visible
  - baking a recap-specific or challenge-specific artifact model into the authored contract
- Would silently foreclose:
  - failing to preserve enough session/snapshot/result identity for a later recap/report shell to exist cleanly
  - or preserving only the kinds of identifiers that suit frozen challenge/result surfaces while leaving recap/report residue underspecified
- Must remain explicit:
  - Phase 1 preserves substrate, not shell order
  - session snapshots, challenge results, and event-memory objects are downstream consumers, not present-tense contract commitments
  - event/editorial wrapper plurality must stay intact

## 8. What each doc may safely imply

- `PROJECT.md` may safely imply that later explicit shells could include post-session recap/report residue, challenge/result residue, or still-later event-memory residue, as long as the layers stay distinct.
- `LONG-ARC.md` may safely imply that explicit post-play shells can appear before a true event object, provided the doc keeps memory and cadence layered.
- `ROADMAP.md` may safely imply that Phase 5 summary/replay protects the seam for later recap/report thinking without claiming that the recap shell is already settled or shipped as doctrine.
- `01-CONTEXT.md` may safely imply that the authored substrate should preserve enough stable identity for later recap/report, featured-result, and event-memory consumers to exist without rewriting Phase 1 contracts.

## 9. What each doc must not imply

- `PROJECT.md` must not imply that the first explicit shell is closed, or that `event container` language already means a scheduled event board is next by default.
- `LONG-ARC.md` must not imply that only true event objects deserve explicit shells, and must not let challenge/result cadence language masquerade as settled event memory.
- `ROADMAP.md` must not imply that Phase 5 summary/replay already answers the full first-shell question, and must not use `featured`, `weekend`, or `event` language as stealth proof that a later event board is first.
- `01-CONTEXT.md` must not imply that Phase 1 has already chosen a recap object, a challenge-result object, or an event-memory object model.

## 10. What must remain explicit

- `hosted-night recap / session report` is the strongest current first explicit shell.
- `featured challenge result` remains the strongest current rival.
- `first explicit shell` and `first true event-memory shell` are separate questions.
- `event memory` still requires a true event object.
- `weekend board / scheduled event board` remains a later true-event-memory seam, not the default first explicit shell.
- permanence, visibility, navigation, cadence, and mastery/history questions remain open and belong to `E2`, not to closure inside `E1`.

## 11. Semantic drift watchpoints

- `event`
  - Do not use it as shorthand for any explicit post-session residue.
- `event container`
  - In canon this is a higher-level shell, not automatic proof that a product surface has crossed into true event-memory territory.
- `summary`, `replay`, `report`, `recap`
  - In-room closeout is not automatically the same as an outward explicit shell, but it is close enough that roadmap wording can accidentally close the question.
- `featured`
  - Can mean editorial prominence, challenge result, or eventized program. Those are not interchangeable.
- `challenge`
  - Can mean frozen participation, share-by-link play, recurring editorial cadence, or visible result shell. The term should not silently settle shell order.
- `weekend`
  - Can signal thematic cadence without proving a true event object.
- `memory`, `history`, `results`
  - These should not collapse into one ledger or one UI promise.

## 12. Sensitivity lane routing

- Lane I: `canon doctrine`
  - primary consumer for `PROJECT.md`, `LONG-ARC.md`, and `01-CONTEXT.md`
  - test whether the canon preserves the separation between recap shell, challenge-result shell, and true event memory
- Lane II: `roadmap and rerun`
  - primary consumer for `ROADMAP.md`
  - test whether Phase 5 summary/replay and Phase 6 carry-forward language preserve the seam without choosing the first explicit shell by accident
- Lane IV: `inquiry debt and anti-hard-coding`
  - primary consumer for the open ordering itself
  - flag any wording that converts "strongest current shell" into "closed winner"
- Lane III: `preserve-only and reversal-sensitive futures`
  - secondary consumer only
  - use this docket if docs start smuggling `weekend board` or other later event-memory shells back in as if they are already the default first explicit shell

## 13. What remains open after this docket

- whether `hosted-night recap / session report` stays ahead of `featured challenge result` across all later archetypes, or only for the current private-first center
- the exact boundary between in-room summary/replay and a revisitable recap/report shell
- the exact amount of identity, history, and residue a `featured challenge result` needs before it pressures the shell order more strongly
- the permanence, visibility, navigation, cadence, and mastery implications of any recap or event-memory surface
- the exact threshold where a named shell deserves true `event memory` language rather than recap/report language
