# 05 Sensitivity Docket E2: Event Memory, Cadence, And Mastery Inquiry Debt Output

## 1. Docket framing

- Mode: `feature-to-doc map`
- Classification: `initial architecture research/planning`
- Purpose: translate the current event-memory, cadence, permanence, and mastery conclusions into doc-level guardrails for sensitivity.
- This docket starts after docket `E1`:
  - `first explicit shell` and `first true event-memory shell` are no longer the same question
  - this docket is about the remaining doctrine and inquiry debt around layered memory, cadence, permanence, and mastery surfaces
- This docket does not choose:
  - a first event-memory UI
  - a permanence ladder
  - a navigation model
  - a cadence taxonomy
  - a first mastery metric

## 2. Target feature pressure

- `event memory` now has a stronger threshold:
  it requires a true event object plus event-scoped residue, not just vivid recap language.
- The docs already preserve layered memory and cadence doctrine, but they still risk collapsing the layers back together in wording.
- `daily/programmed challenge` remains a live pressure point:
  it is currently better read as `editorial/programmed cadence` layered on a play surface, not as automatic proof of a true event object.
- `mastery surface family` is preserved more tightly than before:
  player-owned history, review/explanation, trend/progress, and optional achievement overlay remain thinkable, but no first metric is chosen.
- `room/group memory` is allowed to stay lighter than player history or event memory:
  recap/rematch and recurring-group residue can be real without becoming a heavy permanent archive.
- The open debt is therefore not "should these layers exist?" It is:
  - how durable each layer should be
  - how visible each layer should be
  - how navigable each layer should be
  - which cadence family a named surface belongs to
  - which mastery read appears first

## 3. Current gate classification

- `direct doctrine`
  - player history, room/group memory, event memory, and content calibration/history remain distinct layers
  - `event memory` requires a true event object and event-scoped residue
  - `daily/programmed challenge` is not automatic event memory
  - `mastery surface family yes, first metric no`
- `bounded-open`
  - how explicit room/group memory becomes beyond recap/rematch
  - whether a `featured` or `race-weekend` expression stays an editorial pulse or later becomes a real event object
  - how visible or private early mastery surfaces should be
- `inquiry debt`
  - the first true event-memory surface
  - permanence depth and retention posture for each memory layer
  - navigation model for recap/history/event surfaces
  - exact cadence labels and frequencies
  - the first visible mastery metric or metric mix
- `reversal-sensitive`
  - any wording that treats `featured`, `daily`, `weekend`, or `event` as automatic proof of a true event object
  - any wording that collapses player mastery history, group residue, event memory, and content history back into one default ledger

## 4. Current survivor and strongest rival(s)

- Current survivor bundle:
  - `event memory` is a later distinct ledger, not a generic synonym for recap or history
  - `daily/programmed challenge` is still better translated as editorial/programmed cadence than as event memory
  - `mastery surface family` is real enough to preserve without choosing the metric
  - `room/group memory` can stay real while remaining lighter, shallower, and more visibility-bounded than event memory
- Strongest rival misreads:
  - `featured challenge result`, `hosted-night recap`, or `weekend board` being treated as already the chosen event-memory surface
  - a single permanence ladder for all memory layers
  - a single cadence word standing in for session pacing, behavioral continuity, editorial pulse, and event schedule
  - a single mastery metric or public achievement posture being read as already chosen
- Cross-docket boundary:
  - `E1` owns the first-shell ordering pressure
  - `E2` owns the doctrine and inquiry debt that remain after that separation

## 5. Why this pressure matters

- The canon already uses terms such as `summary`, `replay`, `history`, `challenge`, `event`, `session`, `recurrence`, and `watchable`.
- Without a docket, those words can quietly choose a product shape just by being reused in slightly different places.
- The main risks are:
  - `summary/replay` drifting from in-room residue into implied event memory
  - `daily/programmed challenge` drifting from cadence overlay into implied event object
  - `player history` drifting into the only named future memory layer
  - `mastery` drifting from surface family into one assumed metric or grind system
  - `history` drifting into one shared permanence decision for every layer
- Sensitivity needs this map because a document can stay correctly non-committal about a final event board while still being wrong if it flattens all history, cadence, or mastery language into one bucket.

## 6. Relevant planning surfaces

- `.planning/PROJECT.md`
  - owns the milestone-arc language for `lightweight player identity and session history`, `room/group memory and recurrence surfaces, if earned`, and the explicit layered-memory/layered-cadence posture
- `.planning/LONG-ARC.md`
  - owns the durable doctrine that separates `event container`, `room`, `game instance`, memory layers, cadence layers, and obligation thresholds
- `.planning/ROADMAP.md`
  - owns the practical carry-forward notes where `summary`, `replay`, `recurrence`, and Phase 6 history/calibration wording can accidentally hard-code later surfaces
- `.planning/REQUIREMENTS.md`
  - owns the future capability vocabulary around recurring challenge, player history, replay/review, and the protected seam against one flat ledger
- `.planning/phases/01-authored-round-contract/01-CONTEXT.md`
  - owns the rerun-facing seam language that must preserve later memory layers without importing event-memory or mastery design into Phase 1

## 8. What each doc may safely imply

- `event memory` is a later distinct layer that becomes real only once there is a true event object with event-scoped residue.
- `player mastery history` is a real future family and may become the earliest durable player-owned memory surface without locking its first metric.
- `room/group memory` may stay recap-oriented, rolling, shallow, or visibility-bounded and still count as real.
- `daily/programmed challenge` is currently safer as editorial/programmed cadence layered on a play surface than as event-memory proof.
- Different memory layers may legitimately have different permanence, visibility, and navigation depth.
- `cadence` may safely be discussed as split families:
  - session pacing
  - behavioral/mastery continuity
  - editorial/programmed pulse
  - event schedule

## 9. What each doc must not imply

- that a final event-memory board, archive, or `weekend` surface is already chosen
- that `summary`, `replay`, `recap`, `featured challenge`, and `event memory` are interchangeable
- that all future memory layers share one permanence ladder, one visibility rule, or one navigation model
- that the project has already chosen exact cadence labels such as `daily`, `weekly`, `featured`, or `race-weekend`
- that the first visible mastery read is already `accuracy`, `completion`, `collection depth`, achievements, or any other single metric
- that player history, group residue, event memory, and content calibration/history belong in one default ledger

## 10. What must remain explicit

- `E1` and `E2` are separate:
  `first explicit shell` is not the same question as `first true event-memory shell`.
- `event memory` requires:
  - a true event object
  - event-scoped residue
  - separation from room recap and player mastery history
- `group memory` is allowed to be lighter, shallower, and more private than player history or event memory.
- `mastery surface family` is preserved, but the first metric and first public/private read are still open.
- `editorial/programmed cadence` is preserved as a family, but exact labels, frequencies, and staffing burden remain open.
- permanence, visibility, and navigation are layer-specific questions, not one global history decision.

## 11. Semantic drift watchpoints

- `event`
  - only use it as event-memory proof when schedule, participation boundary, and event-scoped residue are real
- `summary`, `replay`, `recap`, `report`
  - room closeout language is not automatically player history, group memory, or event memory
- `history`, `memory`, `archive`
  - these are not synonyms unless the layer and permanence depth are named
- `cadence`
  - specify whether the meaning is session pacing, behavioral continuity, editorial/programmed pulse, or event schedule
- `mastery`
  - distinguish the return loop, the surface family, and the chosen metric
- `daily`, `featured`, `weekend`, `race-weekend`
  - cadence markers or themed packaging are not automatic event-object proof
- `persistent`
  - persistence should not imply one public profile, one archive depth, or one forever-history promise

## 12. Sensitivity lane routing

- `Lane I: canon doctrine`
  - primary consumer for `PROJECT.md`, `LONG-ARC.md`, and `REQUIREMENTS.md`
  - test whether layered memory/cadence doctrine stays explicit without turning later surfaces into settled product commitments
- `Lane II: roadmap and rerun`
  - primary consumer for `ROADMAP.md` and `01-CONTEXT.md`
  - test whether Phase 5 `summary/replay`, Phase 6 evidence/history language, and Phase 1 seam preservation stay non-committal about event memory, permanence, and mastery metrics
- `Lane IV: inquiry debt and anti-hard-coding`
  - primary consumer for:
    - permanence ladder
    - visibility/navigation depth
    - cadence taxonomy
    - first mastery metric
    - first true event-memory surface
- `Lane III: preserve-only and reversal-sensitive futures`
  - secondary consumer only when docs start treating `featured` or `weekend` language as already-owed event infrastructure or as proof that the event question is settled

## 13. What remains open after this docket

- which later shell, if any, earns explicit event-memory persistence first
- the permanence, visibility, and navigation depth for room/group memory versus player history versus event memory
- whether recurring-group residue needs a named surface beyond recap/rematch, and when
- the exact label set and frequency posture for editorial/programmed cadence
- whether the first mastery read should foreground progress, accuracy, collection depth, achievement overlay, or a hybrid
- how public or private any later mastery or event residue should be
- whether a future `race-weekend` expression remains a themed spotlight or becomes a genuine event object
