# 05 Gap Closure Lane C: Community, Spectator, And Bounded Public Shells

## Lane framing

`[governing:cited]` This lane is a `synthesis` pass over existing audit and canon material, not a blank ideation lane and not a public-platform design pass. The question is which community, spectator, and bounded-public shells belong in the mature-product story, in what order, and with what audience-rights posture, while keeping private trusted-room play as the product center (`05-gap-closure-lane-c-community-shells-task-spec.md:16-24`, `05-gap-closure-synthesis.md:43-47`, `05-gap-closure-lane-common-scaffold.md:23-31`).

`[evidenced:cited]` The external-reference memo anticipated by the closure plan is not yet present in this directory (`05-gap-closure-context-and-plan.md:95`, `114-118`). This output therefore closes the lane at `local-canon doctrine and operating-shape` depth only. It can rank internal shell ordering and deferrals, but it should not overclaim about comparative market plausibility or exact streamer/community patterning on external evidence that has not yet been gathered.

`[assumed:reasoned]` Good stopping point for this lane is narrower than "solve community." It is:

- identify the first credible bounded-public shells after trusted private rooms
- define the rough ladder of audience rights those shells imply
- state what should remain private-first or explicitly deferred
- give later synthesis and sensitivity work a planning-ready shell ordering

## What is already settled

`[governing:cited]` The following doctrine is inherited and should not be casually reopened here:

- private-first play remains the center, and bounded public or spectator value should wrap that center rather than replace it (`05-gap-closure-synthesis.md:43-47`, `PROJECT.md:136-146`)
- streamer-friendliness currently means watchability, role clarity, and later shell preservation, not optimizing the product around public-broadcast culture (`05-gap-closure-context-and-plan.md:45`, `LONG-ARC.md:131-137`)
- visibility is staged, and selectively visible showcase or spectator surfaces are distinct from broader public discovery (`LONG-ARC.md:91-107`, `PROJECT.md:136-146`)
- player, host, and audience surfaces are materially distinct, and audience rights should not be collapsed into generic participation (`05-gap-closure-context-and-plan.md:69`, `round-2b-foreclosure-synthesis-output.md:139-145`)
- memory and cadence stay layered: room/group memory, event memory, player history, and content history are not one flat social ledger (`05-gap-closure-context-and-plan.md:43`, `round-2b-sensitivity-map-output.md:97-112`)
- public live participation, open creator publishing, and stronger public service/moderation obligations remain deferred (`LONG-ARC.md:155-166`, `05-gap-closure-synthesis.md:91-106`)

`[assumed:reasoned]` New closure work in this lane therefore sits above that doctrine. The open job is not "should there be community?" It is "which bounded shells earn their place first, and what should they be allowed to do?"

## Path of inquiry

`[assumed:reasoned]` The inquiry path for this lane was:

- `Entry point` - start from the closure bundle's explicit unresolved question: which bounded community / spectator shells belong in the mature-product story and in what order (`05-gap-closure-synthesis.md:43-47`, `05-gap-closure-context-and-plan.md:69`)
- `Branches considered` - private group-memory surfaces, recap/showcase spillover, live audience shells, streamer-adjacent special events, and more persistent community layers
- `Branches pursued` - shell ordering by obligation cost and product fit; audience-rights ordering; where memory should attach; what must remain private-first
- `Branches deferred or abandoned` - pricing/support posture, open publishing, moderation/governance architecture, exact clip tooling, and the final cadence model
- `Reframing` - the useful comparison is not `community features yes/no`; it is `memory shell -> showcase shell -> bounded live audience shell -> ambient public layer`

`[evidenced:cited]` Round 2A Lane D was useful continuity because it already argued that Prix Guesser's strongest public-facing future looks like appointment layers around authored or hosted play rather than a permanently public social core (`round-2a-lane-d-community-event-output.md:50-59`). Round 2B then sharpened the harder seam questions: distinct audience surfaces, layered rights, layered memory, and staged visibility (`round-2b-sensitivity-map-output.md:77-112`, `round-2b-foreclosure-synthesis-output.md:107-111`, `168-175`).

## Core closure questions

`[assumed:reasoned]` The lane reduces to five practical questions:

1. What is the first credible community/public-adjacent shell after trusted private rooms?
2. What is the first credible live audience shell, if any?
3. Which audience rights belong earlier, and which should stay later?
4. Where should recap, clip, rivalry, and folklore memory attach?
5. How central should streamer-adjacent posture actually be in the mature-product story?

## Findings

### 1. The first bounded-public shell should be selective memory and showcase spillover, not ambient public community

`[evidenced/governing:mixed]` The current doctrine already stages visibility from trusted private rooms to unlisted/share-by-link surfaces and then to selectively visible showcase or spectator shells before any broader public discovery (`LONG-ARC.md:91-107`, `PROJECT.md:136-146`). Round 2A Lane D also points toward public episodes, featured events, and watchable shells rather than a permanently open communal core (`round-2a-lane-d-community-event-output.md:50-59`).

`[assumed:reasoned]` The best first shell after private rooms is therefore not a public social layer. It is a `showcase aftermath` layer:

- recap pages or summaries
- featured outcomes, winners, or rivalries
- highlight or clip-adjacent artifacts
- selectively shareable traces of a room or event

`[assumed:reasoned]` This gives Prix Guesser a community-facing seam without forcing stranger join, public identity defaults, or always-on discourse infrastructure.

### 2. The first live audience shell should be a hosted event wrapper with explicit player, host, and audience separation

`[evidenced/governing:mixed]` Round 2A Lane D's strongest positive picture is an appointment layer around authored or hosted play with a host/editorial frame, a player-facing contest, an audience-readable reveal surface, and an afterward memory surface (`round-2a-lane-d-community-event-output.md:50-57`). Round 2B strengthens why that needs to be a distinct shell: player, host, and audience surfaces are materially different, and visibility-scoped publication is a real seam rather than a cosmetic overlay (`round-2b-sensitivity-map-output.md:77-92`, `round-2b-foreclosure-synthesis-output.md:82-92`, `168-174`).

`[assumed:reasoned]` The first credible live community shell is therefore:

- event-bounded rather than ambient
- hosted or editorially framed rather than fully self-organizing
- selective in audience access rather than open-by-default
- built around reveal readability and aftermath memory rather than constant public chatter

`[assumed:reasoned]` Race-weekend specials, featured rivalry nights, or curated community events fit that shape better than open public rooms.

### 3. Audience rights should ladder upward instead of jumping straight to participation

`[evidenced/governing:mixed]` The audit now treats audience rights as materially distinct from player rights, and it warns against flattening audience entry into the same flow as player participation (`05-gap-closure-context-and-plan.md:69`, `round-2b-sensitivity-map-output.md:69-92`, `148-158`). The room/admin/operator/judge/audience distinction is also already part of the non-foreclosure doctrine (`round-2b-foreclosure-synthesis-output.md:90-92`, `141-145`).

`[assumed:reasoned]` The safest and most coherent audience-rights ladder is:

1. `read / recap rights`
2. `watch live rights`
3. `light reaction or prediction rights`, only where they do not distort private play or reveal structure
4. `active stranger participation` only as a later, explicitly re-scoped decision

`[assumed:reasoned]` This is a substantive closure point. The product does not need to decide now whether it will ever support broad live audience participation. It does need to stop speaking as if all "community" rights arrive together.

### 4. Streamer-adjacent posture is a compatibility target and periodic amplifier, not the core mature-product engine

`[evidenced:cited]` The closure synthesis itself classifies stronger strategic dependence on streamer-adjacent growth as a lower-confidence target, not a confirmed pillar (`05-gap-closure-synthesis.md:76-84`). The long-arc doctrine says the current meaning of spectator-friendly is watchability, role clarity, and safe seams for later shells, not optimization around public broadcast culture (`LONG-ARC.md:131-137`).

`[assumed:reasoned]` The right carry-forward is therefore modest but real:

- preserve hostable reveal rhythm
- preserve readable audience surfaces
- keep streamer-hosted specials viable as one hosted-event variant
- do not let streamer growth become the main argument for community-shell sequencing

`[assumed:reasoned]` In practice, `streamer-adjacent` reads more like a good stress test of shell quality than a ranking argument for product centrality.

### 5. Community memory should attach first to room and event layers, not to ambient public identity

`[evidenced/governing:mixed]` The mature-product gap remains partly open because the repo still needs clearer room/group/event-memory vocabulary (`05-gap-closure-context-and-plan.md:70`). Round 2B sensitivity work is explicit that room/group memory, event memory, player history, and content calibration history should not collapse into one ledger (`round-2b-sensitivity-map-output.md:97-112`, `159`). Round 2A also already concluded that privacy is not the opposite of community and that recurrence often begins privately before it becomes public (`round-2a-experience-archetypes-output.md:219-239`).

`[assumed:reasoned]` The first social-memory surfaces should therefore be:

- room or group folklore
- event recap and featured outcomes
- rivalry traces and notable calls
- clip/quote/highlight surfaces attached to a room or event wrapper

`[assumed:reasoned]` Public profiles, ambient feeds, or broad public collections may remain possible later, but they should not become the default memory substrate for this lane's first closure answer.

### 6. The strongest community answer is a staged shell ladder, not one universal "community layer"

`[assumed:reasoned]` Integrating the findings above yields a cleaner operating model:

- `private room core`
- `private/group memory shell`
- `selective showcase aftermath shell`
- `hosted bounded live audience shell`
- `later persistent community layer`, if the project deliberately accepts stronger identity, moderation, and service obligations

`[assumed:reasoned]` This is the main new closure work from the lane. It preserves the repo's private-first center while giving mature-product synthesis a positive answer stronger than "community features remain possible."

## Live options or operating shapes

`[assumed:reasoned]` Several shapes are still alive, but they do not deserve equal rank:

| Operating shape | Description | Strengths | Main risks | Lane status |
| --- | --- | --- | --- | --- |
| `Private-memory spillover` | recap, highlights, featured outcomes, rivalry traces, selectively shareable aftermath | low obligation, fits private-first doctrine, strengthens group memory | can be too thin if treated as the whole community answer | first-ranked |
| `Hosted showcase / event shell` | bounded live audience around a curated event, pack, or rivalry night | strongest watchability fit, clearest player/host/audience separation, fits race-weekend cadence | needs explicit audience rights and host/editorial authority | second-ranked and likely first live shell |
| `Streamer-hosted special` | creator or host uses the showcase shell as a readable special event | good amplifier, good stress test of watchability | too dependent on host charisma; easy to over-center as growth theory | keep alive as a variant, not a pillar |
| `Persistent ambient community layer` | public profiles, discussion, broad collections, always-on community identity | could deepen social persistence later | pulls in identity, moderation, discovery, and obligation shifts too early | explicitly later / not first-ranked |

`[assumed:reasoned]` The ordering matters. The first two shapes fit the current doctrine cleanly. The fourth one is not ruled out forever, but it is under-supported and obligation-heavy relative to the rest of the mature-product bundle.

## Recommended carry-forward

`[projected:reasoned]` Recommended shell ordering for later synthesis and canon-sensitive carry-forward:

1. keep `private room + room/group memory` as the foundation
2. rank `selective recap/showcase spillover` as the first bounded-public shell
3. rank `hosted bounded live audience` as the first credible live public-adjacent shell
4. treat `streamer-hosted specials` as one operating variant of the hosted shell, not as a separate product center
5. keep `persistent ambient community layer` explicitly later and conditional

`[projected:reasoned]` Consequences for the converged mature-product synthesis:

- it should describe community as a staged shell ladder around private-first play, not as one generic bucket of future features
- it should distinguish `memory shell`, `showcase shell`, and `live audience shell`
- it should keep `audience rights` separate from `player participation`
- it should treat public-shell recurrence as one return layer, not the master answer to retention

`[projected:reasoned]` Consequences for later canon patching, if this lane survives synthesis and sensitivity testing:

- `PROJECT.md` should likely name room/group memory, recap/showcase spillover, and bounded live audience shells more explicitly
- `LONG-ARC.md` should likely extend the visibility ladder so `showcase aftermath` and `bounded live audience` are more explicit than the current generic spectator shell wording
- `ROADMAP.md` should likely add carry-forward notes for audience-only access, event-wrapper memory, and non-collapse of player/host/audience surfaces in later phases
- `REQUIREMENTS.md` should likely strengthen reference anchors around audience rights and separated room/group/event memory without turning them into new Milestone 1 ship-gates

## Explicit deferrals

`[open:reasoned]` This lane does not close, and recommends continuing to defer:

- open public room discovery or stranger-join rooms
- ambient public profiles, broad social feed, or generic discussion layer as an early shell
- open creator publishing, marketplace behavior, or broad community-authoring governance
- exact moderation, governance, or trust-and-safety architecture for public participation
- exact clip tooling, final event-wrapper taxonomy, or durable public standings structures
- pricing, support, premium, or hosting economics
- exact ranking of all recurrence layers beyond this lane's bounded-public contribution
