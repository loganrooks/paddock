# 05 Residual Gap Chunk C: Later Hosting-Branch Discrimination And Service Identity

## Chunk framing

- Mode: `synthesis`
- Classification: `initial architecture research/planning`
- Question:
  after the remediation host packet, what actually differentiates `official hosted convenience` from `sanctioned mirrors / collectives`, which of those comparisons are true later rankings versus different branch identities, and what may the later sensitivity pass honestly assume?
- Scope:
  - later comparison after `trusted operators`
  - service identity versus governance identity
  - host-mode metadata and promotion thresholds
  - operator burden, governance-failure evidence, succession/shutdown burden, and money-family coupling
- Non-goals:
  - not reopening browser P2P as a main branch
  - not designing final pricing, legal contracts, or operator tooling
  - not ranking large-scale public infrastructure strategies
  - not forcing one universal later-host winner
- Stop condition:
  enough direct external grounding exists to state what has tightened, what remains challengeable, and what still prevents a clean later host ladder from being treated as settled

`[evidenced:cited:internal]` These belong together because the remediation host packet already did the first repair:

- it strengthened `trusted operators` as the first transition seam
- it separated `trusted operators`, `official hosted convenience`, and `sanctioned mirrors / collectives`
- it refused a final ranking between the later two branches

`[open:reasoned:internal]` The residual gap is narrower:

- whether the later comparison is actually one ladder at all
- whether `official hosted convenience` is best understood as a later `service identity` branch
- whether `sanctioned mirrors / collectives` are best understood as a later `governance identity` branch
- which thresholds and user-facing metadata would make either branch coherent enough to promote

`[governing:cited:internal]` This chunk is not trying to close:

- exact pricing or entitlements
- exact host contract text
- detailed operator tooling
- public-first discovery or stranger participation
- a final roadmap commitment to either later hosting branch

## What is already settled

`[evidenced:cited:internal]` The current canon and remediation packet already settle:

- the project center remains `private-first`, `browser-first`, `host-led`, and `watchable`
- one canonical authoritative bundle and stable browser-first guest join grammar must be preserved across hosting branches
- `trusted operators running the canonical authoritative bundle` is the strongest first transition seam
- `official hosted convenience` remains a live later branch
- `sanctioned mirrors / collectives` remain a live branch family, but not an obvious next rung
- host-mode labeling and support-boundary clarity are required wherever more than one host form is visible

`[evidenced:cited:internal]` The deferral review also already corrected key terms:

- `official hosted convenience as a first-value branch` is `rejected-for-now`
- `sanctioned mirrors / collectives as a promoted branch` are `rejected-for-now`
- both later families remain preserved, but not as near-term commitments

## What remains live

`[open:reasoned:internal+external-direct]` The live uncertainty is no longer `does hosting matter?` It is:

- whether the later comparison should be treated as one ladder or as two partially different product identities
- whether `official hosted convenience` is the stronger later branch if the project wants one accountable, low-friction remote service
- whether `sanctioned mirrors / collectives` are only coherent if the project is willing to become a curator and reviewer of hosts
- what minimum host metadata users would need to distinguish:
  - private trusted operator
  - official hosted service
  - promoted third-party host
- where hosting joins the money-family story and where it should stay separate from support posture
- what remains too underdescribed to let sensitivity talk as if there were one clean later host ladder

## Reference translation

### Foundry

- What is analogous:
  - one authoritative host with many browser clients
  - a non-creator operator can host the canonical software bundle
  - self-hosted, cloud-hosted, and partner-hosted modes create meaningfully different burden profiles
- What is not analogous:
  - campaign persistence and GM identity do not map directly to Prix Guesser room identity
  - licensing policy is not a product-governance template for Prix
- What is borrowed as concern:
  - `trusted operator` is a real pattern, not a hypothetical
  - `always on` convenience solves a different problem than `someone else can host`
  - network and runtime burden remain real even with one canonical bundle
- Semantic drift flagged:
  - Foundry's `partner-hosted` language is evidence for convenience outsourcing, not evidence for a project-curated collective-governance branch

### Mastodon

- What is analogous:
  - once a project promotes third-party hosts, standards and review become unavoidable
  - contactability, backup/recovery, emergency access, and shutdown notice become part of the user-trust surface
  - a host program can fail if listings exist without quality control
- What is not analogous:
  - Mastodon is far more public, social, and moderation-heavy than current Prix doctrine
  - federation itself is not the borrowed solution here
- What is borrowed as concern:
  - promoted hosts imply governance work, not just extra capacity
  - host identity has to be legible to users
  - abandonment and failure modes must be planned before promotion
- Semantic drift flagged:
  - `server` in Mastodon often means a public social home. Here it is being borrowed only as evidence about promoted-host governance burden, not as evidence that Prix should become a federated public network

### Home Assistant / Nabu Casa

- What is analogous:
  - official convenience can sit above a more operator-heavy base system
  - remote access, backups, and account management create a distinct service layer
  - the convenience layer can carry recurring cost and service-side enforcement
- What is not analogous:
  - Home Assistant Cloud is not a multiplayer game-hosting service
  - its core product is local device control, not live room orchestration
- What is borrowed as concern:
  - `official hosted convenience` is not just packaging; it creates a separate account, subscription, support, and security-enforcement surface
  - the convenience layer can be withdrawn if the underlying instance or account state is wrong
- Semantic drift flagged:
  - `cloud` in Home Assistant means a managed convenience/service layer over a local system. Here it is being used to sharpen `service identity`, not to claim that Prix's official hosting would work the same way technically

## Negative-case / failure evidence note

`[evidenced:cited:external-direct]` The negative-case evidence is strong enough to matter directly:

- Mastodon explicitly abandoned automatic server listing because it produced no reliable quality signal and did not distinguish good community options from bad ones.
- The Mastodon covenant requires backups, emergency contact/access, and advance shutdown notice precisely because promoted hosts can disappear, drift, or fail users.
- Foundry's self-hosted mode is only reachable while the host is online and correctly configured; cloud/partner hosting trade that burden for cost and vendor dependence rather than removing it.
- Nabu Casa's remote-access service can stop working when the local instance is disconnected, the wrong cloud account is used, or the underlying instance is too insecure.
- Cancelling the official cloud service removes convenience features such as remote access and cloud backup.

`[assumed:reasoned:internal+external-direct]` The practical implication is:

- `official hosted convenience` creates failure modes that look like `service outage`, `account problem`, or `security enforcement`
- `sanctioned mirrors / collectives` create failure modes that look like `host abandonment`, `compatibility drift`, `unclear support owner`, or `promotion without quality control`

Those are not the same risk family, so they should not be flattened into one later rung.

## Live alternatives

| Branch | Primary problem solved | User-visible identity | Burden center | Comparative status now |
| --- | --- | --- | --- | --- |
| `trusted operators` only | reduce Logan-only dependence inside bounded trusted groups | still one private product with informal operator variation | technical setup and recovery on known operators | remains the first transition seam |
| `official hosted convenience` | reduce room-start fragility, always-on pain, and coordination overhead under one accountable surface | one official service identity with distinct account/support expectations | central service operation, billing/support, security/update enforcement | strongest later branch if the product wants one low-friction official remote surface |
| `sanctioned mirrors / collectives` | support plural promoted hosts, geography/resilience spread, or distributed stewardship | a governed multi-host ecosystem with explicit host distinctions | standards, review, compatibility discipline, backup/shutdown/contact policy, ongoing governance | remains live, but as a different later identity family rather than a clean next rung |
| `official hosted convenience + unpromoted private operators` | keep one official convenience path without turning informal operators into a promoted network | official surface plus clearly unsupported private host variants | split between official service burden and private operator autonomy | plausible hybrid later shape; weak evidence that promoted collectives are needed before this hybrid is exhausted |

## Findings

### Direct evidence

`[evidenced:cited:external-direct]`

- Foundry directly supports a bounded `trusted operator` pattern and separately supports cloud/partner hosting as an `always on` convenience path.
- Mastodon directly shows that promoted hosts require review standards, metadata, backups, emergency access, and shutdown posture.
- Mastodon also provides a direct failure case for naive host directories: promotion without quality control is not neutral.
- Home Assistant / Nabu Casa directly shows that an official convenience layer creates:
  - separate account identity
  - recurring service economics
  - remote-access dependency on the service
  - service-side security enforcement

### Inference and interpretation

`[assumed:reasoned:internal+external-direct]`

1. `Official hosted convenience` and `sanctioned mirrors / collectives` are not merely two later points on the same line.

   - `Official hosted convenience` is a `service identity` branch.
   - `Sanctioned mirrors / collectives` are a `governance identity` branch.
   - Both are later than `trusted operators`, but they solve different problems and create different obligations.

2. The sharper comparison is not `which branch comes next?` It is:

   - `Do we want one accountable official service surface?`
   - `Do we want a promoted plural-host ecosystem we are willing to police?`

3. If the project's later goal is `one low-friction remote surface without turning Prix into a host curator`, `official hosted convenience` is the stronger later branch.

   Why:

   - it preserves one canonical service identity
   - it keeps guest comprehension simpler
   - it better matches the current private-first, browser-first, one-authoritative-bundle doctrine

4. If the project's later goal is `distributed stewardship, geography spread, or resilience through multiple promoted operators`, `sanctioned mirrors / collectives` remain alive but only as a more radical product-identity shift.

   Why:

   - the branch requires standards, review, contactability, shutdown posture, and compatibility discipline
   - those are governance commitments, not just technical extensions

5. The residual gap is therefore no longer `host ecology is blurry in general`.

   It is:

   - how much `official hosted convenience` should be preserved as the stronger later branch
   - whether `sanctioned mirrors / collectives` should remain preserve-only unless the product deliberately chooses plural-host governance identity
   - what minimum metadata and support language would be needed if both branches stay visible

6. `Host-mode metadata` is not cosmetic.

   Once more than one host form is visible, users likely need at least:

   - host type: `private trusted operator`, `official hosted`, `promoted third-party`
   - authority/compatibility state
   - support owner/contact path
   - persistence/availability expectation
   - data/recovery or shutdown posture at a coarse level

7. Hosting and the money-family story intersect, but only asymmetrically.

   - `official hosted convenience` naturally touches recurring cost, support obligation, and service identity
   - `sanctioned mirrors / collectives` primarily touch governance and trust language first, and only secondarily touch money

## What got tighter

`[evidenced:mixed:internal+external-direct]`

- `Official hosted convenience` is now tighter as a branch concept:
  it is no longer just `hosted later`; it is `a distinct official service layer with account, support, recurring-cost, and enforcement implications`.
- `Sanctioned mirrors / collectives` are now tighter as a branch concept:
  they are no longer just `more hosts later`; they are `a promoted host-governance program with review and failure-management obligations`.
- The later comparison is tighter:
  `official hosted convenience` is stronger on the one-service, low-friction, accountable-service axis.
- The non-comparability is also tighter:
  `sanctioned mirrors / collectives` should not be treated as just a later or larger version of official hosting.
- The required user-facing distinction is tighter:
  if the project ever exposes more than one host mode, host identity and support identity must be legible, not implicit.

## What remains challengeable

`[open:reasoned:internal+external-direct]`

- whether `official hosted convenience` should stay merely preserved or become the clearly preferred later branch
- whether a hybrid `official hosted convenience + unpromoted private operators` shape removes most of the practical need for promoted collectives
- whether `sanctioned mirrors / collectives` are ever worth the review and governance burden for a product that remains private-first for a long time
- exactly which host metadata fields users would need first
- whether later event/showcase shells increase the value of one official service surface enough to change the later ranking
- how sharply the product could separate official and promoted-host support boundaries without confusing users

## First-value vs later-value

| Branch | First-value in the transition phase | Later-value in a broader mature product | Preserve without prioritizing? |
| --- | --- | --- | --- |
| `trusted operators` | high: best early way to reduce Logan-only hosting without changing the product's identity much | medium: still useful later, but less identity-shaping than the other two branches | no; this remains the main carry-forward seam |
| `official hosted convenience` | low-medium: not first unless always-on access, room-start reliability, and scheduling pain dominate | high if the project wants one official, low-friction remote surface with one support owner | yes, and more strongly than promoted collectives |
| `sanctioned mirrors / collectives` | low: too governance-heavy for the current transition phase | medium only if the project later wants plural promoted hosts and accepts the curator/reviewer role | yes, but as preserve-only unless the product deliberately chooses that identity |
| `official hosted convenience + unpromoted private operators` | medium: can coexist with the first transition seam without forcing a host-governance program | high if the project wants one official convenience path while still permitting informal private autonomy | yes; this hybrid remains materially live |

## Archetype-to-burden translation

| Archetype | `official hosted convenience` | `sanctioned mirrors / collectives` | Comparative reading |
| --- | --- | --- | --- |
| `private recurring group` | useful only if host uptime/availability repeatedly breaks the ritual | usually overbuilt; governance burden exceeds the value of promotion | official convenience is more coherent than promoted collectives if this archetype drives later hosting |
| `private online sync across known friends` | strong later fit if always-on remote access and coordination simplicity matter | still weak unless multiple trusted groups need promoted external operators | official convenience is the stronger later branch on this archetype |
| `solo ritual / async personal use` | later convenience value possible if persistence and cross-device access matter | very weak | collectives have little first-order value here |
| `bounded event / showcase shell` | can become attractive because one official surface is easier to explain publicly or semi-publicly | could matter only if the project wants multiple promoted event hosts and can label them brutally clearly | event/showcase pressure is the main archetype that can later strengthen official hosting relative to private trusted operators |

`[assumed:reasoned:internal+external-direct]` This chunk does not show one archetype where promoted collectives clearly beat official hosted convenience without the project first deciding it wants a governed plural-host identity.

## Trigger conditions

| Branch or shift | Promote when | Hold / defer when |
| --- | --- | --- |
| `trusted operators` -> `official hosted convenience` | repeated room-start failures, always-on demand, host-availability pain, or guest setup friction dominate; the project is willing to own one service identity, support path, and security/update enforcement posture | most value still comes from bounded trusted groups; informal operators solve the real pain; the project does not want stronger service obligation yet |
| preserve `official hosted convenience` more strongly than `sanctioned mirrors / collectives` | the product wants one canonical remote surface, one support owner, and simpler guest comprehension | the product intentionally wants distributed stewardship or geography spread more than one official service surface |
| `trusted operators` -> `sanctioned mirrors / collectives` | there is a real need for multiple promoted hosts; the project can publish and enforce standards; compatibility, backup, contact, review, and shutdown posture can all be checked | host demand is still mostly informal/private; review capacity is missing; user trust would blur promoted hosts with one official service |
| expose multiple visible host modes | users can understand host type, support owner, and compatibility state from clear metadata and labeling | host distinctions would still be opaque or socially confusing |
| join hosting to the money-family story | recurring costs, uptime expectations, and support obligations become explicit enough that official convenience would otherwise be under-described | the product is still in optional-support territory and does not want hosting to imply service obligation |

## Recommended carry-forward

1. Carry forward that there is **not** one clean later host ladder after `trusted operators`.
2. Carry forward `official hosted convenience` as the stronger later branch on the `one accountable service identity` axis.
3. Carry forward `sanctioned mirrors / collectives` as a different `governed plural-host identity` branch, not as an automatic next rung.
4. Preserve `official hosted convenience + unpromoted private operators` as a live hybrid later shape.
5. Require explicit host-mode metadata if more than one visible host form ever exists.
6. Keep `official hosted convenience` tied to later service and money-family questions.
7. Keep `sanctioned mirrors / collectives` tied to governance, promotion, and failure-management questions first.
8. Treat any future promotion of collectives as a deliberate product-identity decision, not as a passive scaling step.

## What should remain open

`[open:reasoned:internal+external-direct]`

- whether `official hosted convenience` ever becomes active product priority rather than a preserved later branch
- whether the project ever wants a promoted plural-host identity at all
- whether official hosting and promoted collectives could coexist without collapsing user trust boundaries
- which minimal host metadata fields would be enough in the first visible multi-host moment
- how much later showcase/event pressure is needed before official hosting becomes materially stronger than continued trusted-operator expansion

## Sensitivity implications

`[governing:reasoned:internal+external-direct]` The later sensitivity pass may now assume:

- `trusted operators` remains the first transition seam
- `official hosted convenience` and `sanctioned mirrors / collectives` are different later branch identities, not one settled ladder
- host-mode labeling, support identity, and compatibility clarity are load-bearing seams
- `official hosted convenience` is the stronger preserved later branch if the criterion is one official low-friction remote surface

`[governing:reasoned:internal+external-direct]` The later sensitivity pass may **not** assume:

- that `official hosted convenience` is fully chosen as the later winner
- that `sanctioned mirrors / collectives` are just a later or bigger version of official hosting
- that multi-host promotion can be discussed without governance, shutdown, backup, and review burden
- that the money/service implications of official hosting are already resolved
- that there is enough closure to speak as if a clean later host ladder now exists

`[governing:reasoned:internal]` Semantic drift the sensitivity pass should flag if it reappears:

- using `hosted` as if it always means `official service`
- using `community host` as if it were the same thing as `trusted operator`
- using `mirror`, `collective`, and `official hosted` as if they were interchangeable convenience tiers

## What later residual synthesis must reconcile

`[assumed:reasoned:internal+external-direct]` Later residual synthesis should reconcile this chunk with:

- the money-family chunk:
  `official hosted convenience` naturally touches recurring service obligation; `sanctioned mirrors / collectives` do not map cleanly to the same promise story
- the wrapper/community chunk:
  bounded event or showcase shells may increase the later value of one official hosted surface
- the contribution/discovery chunk:
  promoted hosts and promoted content both change endorsement language and user trust boundaries
- the long-arc doctrine:
  any later host branch still has to preserve one canonical authoritative bundle, browser-first guest join, and modest current obligations until the product deliberately changes them

`[open:reasoned:internal]` The main unresolved synthesis question is:

- whether the mature hosting story is best expressed as `trusted operators first, official hosted convenience later, collectives preserve-only`
- or as `trusted operators first, then a hybrid official-plus-private ecosystem, with promoted collectives kept only as a guarded long-arc seam`
