# 05 Pre-Sensitivity Challenge C: Later Hosting-Branch Ordering And Hybrid Host-Service Shape

## Challenge framing

- Mode: `hypothesis testing`
- Classification: `initial architecture research/planning`
- Question:
  does the current stronger-default hosting framing survive when it is compared not only against heavy `sanctioned mirrors / collectives`, but also against the stronger rival of a curated `partner/provider host` ecosystem that preserves self-hostable core software without forcing Prix to become the service operator?
- Scope:
  - stress-test the current ordering after `trusted operators`
  - stress-test whether `official hosted convenience` is actually the strongest serious later branch
  - stress-test whether `official hosted convenience + unpromoted private operators` is a robust hybrid or only a superficially tidy one
  - separate `service identity`, `provider ecosystem identity`, and `collective governance identity`
  - use direct external comparison, not only carry-forward from residual chunk C
- Non-goals:
  - not reopening browser P2P as a main branch
  - not designing final infrastructure, contracts, or operator tooling
  - not choosing an exact host metadata schema
  - not turning this into a roadmap commitment
- Stop condition:
  enough direct external comparison exists to judge whether the current stronger-default frame survives adversarial comparison, weakens, or needs a cleaner branch map before sensitivity

## Target hypothesis

`[evidenced:cited:internal]` The current residual synthesis and chunk C lean toward:

- `trusted operators` as the first hosting seam
- `official hosted convenience` and `sanctioned mirrors / collectives` as different later identities
- `official hosted convenience` as the stronger preserved later branch on the `one accountable service identity` axis
- `official hosted convenience + unpromoted private operators` as a plausible hybrid later shape

## Why this hypothesis matters

`[governing:cited:internal]` This hypothesis matters because it shapes what the later sensitivity pass is allowed to protect directly versus keep open:

- `RGR-03` is specifically about later host-branch thresholds and comparison quality
- `GCO-07` warns that the bundle is still under-grounded exactly where it moves from valid family space into ranking
- `GCO-08A` warns that the project may be mistaking different hosting identities for one simple ladder
- `GCO-08C` warns that `first-value` and `later-value` may still be sliding into each other

`[assumed:reasoned:internal]` If this framing is over-read now, the likely damage is not only wording drift. It would distort:

- long-arc hosting posture
- support and money-family assumptions
- what kind of host metadata later becomes necessary
- whether the project quietly drifts toward `running a service` instead of `shipping software plus bounded hosting paths`

## Gap justification

`[evidenced:cited:internal]` The current stronger-default frame deserves challenge because residual chunk C likely won a real comparison on one axis while still leaving another rival under-described:

- it did real work separating `service identity` from `governance identity`
- it productively rejected treating `collectives` as an automatic next rung
- but it mostly compared `official hosted convenience` against the heaviest plural-host framing

`[assumed:reasoned:internal+external-direct]` The challenge risk is therefore:

- `official hosted convenience` may look stronger partly because the rival branch was framed as `sanctioned mirrors / collectives`
- the strongest practical rival may instead be `curated third-party providers / promoted managed hosts`
- that rival is lighter than `collectives`, but more structured than `unpromoted private operators`

`[governing:cited:internal]` This packet is not re-litigating:

- private-first product center
- browser-first guest access
- self-hostable authoritative rooms as the core seam to preserve
- rejection of full browser P2P as the main branch

## What is already settled and not being relitigated

`[evidenced:cited:internal]` Carry-forward doctrine that stands unless explicitly contradicted:

- the product center remains `private`, `watchable`, `browser-first`, and `host-led`
- `trusted operators running the canonical authoritative bundle` remains a real and important transition seam
- `official hosted convenience` remains live as a later branch
- plural-host futures remain preserved as seams, not dead branches
- if more than one host form is visible, host identity and support identity must be legible
- sensitivity must not promote `official hosted convenience` into a chosen roadmap commitment
- sensitivity must not demote plural-host futures into dead branches simply because they are preserve-only

## Strongest rival framing(s)

`[assumed:reasoned:internal+external-direct]` The strongest rivals are not identical. That matters.

### Rival A: Curated provider / partner-host ecosystem

- `trusted operators` first
- later convenience arrives primarily through promoted managed hosts or certified providers
- Prix remains the canonical software/trust anchor, but does not have to become the main service operator
- convenience is delegated; host labeling and support boundaries become explicit
- this is the strongest rival to `official hosted convenience`

### Rival B: Standardized self-host plus bounded provider guidance

- `trusted operators` first
- official first-party hosting stays preserve-only until a one-support-owner service is clearly earned
- the project invests in better packaging, operator clarity, and possibly a small recommended-host surface before it invests in running official hosting
- this is the strongest rival to the current `official hosted convenience + unpromoted private operators` hybrid

### Rival C: Governed plural-host identity

- `trusted operators` first
- later the project deliberately chooses a multi-host governance identity with standards, review, shutdown posture, and compatibility discipline
- this is closer to the current `sanctioned mirrors / collectives` framing
- it is still a real rival, but it is not the strongest everyday rival to official hosted convenience

`[assumed:reasoned:internal+external-direct]` The main stress-test result already visible here is semantic:

- `promoted provider ecosystem` and `collective governance branch` are not the same rival
- if they are merged into one label, `official hosted convenience` gains advantage by comparison against the heavier branch only

  - `RGR-03`, `GCO-07`, `GCO-08A`, and `GCO-08C`
- Branches considered:
  - accept the current `official hosted convenience` > `collectives` stronger-default frame
  - compare against partner-host/provider ecosystems rather than only collectives
  - compare against hybrid official-plus-private ecosystems for identity clarity
  - revisit public/decentralized precedents only where they clarify governance burden
- Branches pursued:
  - `Foundry VTT` for trusted operators plus official partner-host convenience
  - `Nextcloud` for quality-provider and certified-partner programs
  - `WordPress` for official managed hosting plus recommended hosts plus identity/support boundary stress
  - `Element / Matrix` for official cloud plus self-host/provider plurality plus explicit ecosystem-choice framing
  - `Mastodon` for the heavier governance threshold when a project actively promotes community hosts
- Branches deferred or abandoned:
  - exact SLA, billing, and legal contract design
  - public server directory mechanics for Prix itself
  - final host metadata schema
  - large-scale public/community topology
- Unexpected branches / reframings:
  - the key missing rival is not `collectives beat official hosting`
  - it is `provider ecosystem beats official first-party hosting`
  - the hybrid issue is not only plausibility; it is whether mixed host identities stay understandable at all

## Reference translation

`[assumed:reasoned:internal+external-direct]` The references divide into three useful analog families.

### Family 1: Canonical software plus promoted providers

- `Foundry`, `Nextcloud`, and `WordPress.org` all show that a project can:
  - preserve self-hosted core software
  - direct users to managed providers
  - maintain some listing or partnership criteria
  - avoid making first-party official hosting the only mature convenience answer
- What this translates to for Prix:
  - `promoted provider / partner host` is a real candidate branch
  - it should not be collapsed into `collective governance`

### Family 2: Official hosted convenience plus identity/switching complexity

- `WordPress.com` and `Element Cloud` show the appeal of one accountable hosted surface
- `WordPress.com vs WordPress.org` and Element's rebrand note also show that mixed official/non-official ecosystems require ongoing explanation
- What this translates to for Prix:
  - official hosting can be attractive
  - but hybrid clarity is a product burden, not a free side-effect

### Family 3: Promoted community hosts with heavier governance

- `Mastodon` shows what happens when a project actively endorses host communities rather than just providers
- quality control, moderation, shutdown notice, metadata, and manual review become unavoidable
- What this translates to for Prix:
  - `collectives` remain a meaningfully heavier identity than promoted providers
  - residual chunk C was right to treat them as different from first-party official service

`[assumed:reasoned:internal+external-direct]` Semantic drift flagged explicitly:

- `promoted third-party host`
- `provider`
- `partner host`
- `mirror`
- `collective`

should not be treated as interchangeable. The current stronger-default framing likely compresses the first three into the last two too quickly.

## Negative-case / counterexample note

`[evidenced:cited:external-direct]` Several direct counterexamples matter here:

- WordPress.com's own guide includes `Is my site on WordPress.com or WordPress.org?` and a `Site Profiler` for people who cannot tell where a site is hosted.
- Element says its earlier multiple names were causing confusion once there were many Matrix clients, hosting providers, and companies in the ecosystem.
- Mastodon says the earlier automated server-listing approach failed because it could not provide quality control and simply listed every submitted server.

`[assumed:reasoned:internal+external-direct]` The negative-case implication is:

- hybrid official-plus-non-official ecosystems are not naturally legible
- promoted host programs are not neutral directories
- the current hybrid `official hosted convenience + unpromoted private operators` should be treated as plausible but operationally fragile, not as a clean default

## Evidence that strengthens the current hypothesis

### Direct evidence

`[evidenced:cited:external-direct]`

- Foundry directly supports `trusted operator` hosting and treats managed convenience as a later step for users who want cloud advantages without handling setup alone.
- WordPress.com and Element Cloud show why one official hosted surface can be attractive: one accountable support owner, managed infrastructure, and a clearer service package.
- Mastodon's covenant confirms that promoted community hosts require real governance work; this supports the claim that `collectives` are not just a slightly later convenience tier.

### Inference and interpretation

`[assumed:reasoned:internal+external-direct]`

- `trusted operators` still survives as the first hosting seam better than any other branch tested here.
- `official hosted convenience` and `collective governance` are genuinely different later identities.
- the current synthesis was correct that plural-host governance should not be smuggled in as a passive scaling step.

## Evidence that weakens or complicates it

### Direct evidence

`[evidenced:cited:external-direct]`

- Foundry's mature convenience answer is not first-party official hosting; it is an official partner-host program layered on top of self-hosted software.
- Nextcloud explicitly says private and small-business users are usually best served by quality providers in its `Simple Signup` program, and larger organizations by qualified partners.
- WordPress.org curates recommended hosts and host-feedback flows rather than treating WordPress.com as the only mature convenience path.
- Element explicitly markets self-hosting, private cloud, official cloud, and provider choice together, while emphasizing `competitive ecosystem` and `no vendor lock-in`.
- WordPress and Element both expose identity-explanation overhead once official and third-party hosting live side by side.

### Inference and interpretation

`[assumed:reasoned:internal+external-direct]`

- the strongest rival to `official hosted convenience` is not only `collectives`; it is `curated provider / partner-host ecosystem`
- current stronger-default framing likely overstates how radical non-official later hosting is because it compares official service mostly against the heaviest plural-host branch
- `official hosted convenience + unpromoted private operators` is less stable than residual chunk C implies because it relies on users intuiting support and compatibility boundaries that other ecosystems have to explain constantly

## Comparative verdict

`[assumed:reasoned:internal+external-direct]` Overall hypothesis status: `weakened, not rejected`

| Sub-claim | Verdict | Why |
| --- | --- | --- |
| `trusted operators` is the first hosting seam | `survives` | direct external comparison still supports this as the lowest-obligation transition |
| `official hosted convenience` and `collectives` are different later identities | `survives` | public/community-governance evidence still separates these branches clearly |
| `official hosted convenience` is the strongest serious later branch | `weakened / underdetermined` | a lighter `partner/provider host` rival is strong enough that official first-party service is not clearly the dominant later answer |
| `official hosted convenience + unpromoted private operators` is the main plausible hybrid | `weakened` | plausible, but identity/support confusion is a first-order risk rather than a side note |

`[assumed:reasoned:internal+external-direct]` The main adversarial result is:

- the current frame should not move into sensitivity as if the real later choice is only:
  - `official hosted convenience`
  - versus `sanctioned mirrors / collectives`
- the better bounded map is:
  - `official first-party hosted convenience`
  - `curated provider / partner-host ecosystem`
  - `collective / mirror governance branch`
  - `unpromoted private operators`

`[assumed:reasoned:internal+external-direct]` In that map:

- `official hosted convenience` still stays live and meaningful
- `collectives` still stay heavier and preserve-only
- but `promoted provider / partner host` becomes the strongest rival that the current stronger-default framing did not compare hard enough

## What would falsify or materially re-rank the hypothesis

`[open:reasoned:internal+external-direct]`

- `official hosted convenience` would materially rise if:
  - real user demand concentrates around one official URL, one support owner, always-on availability, and zero host-choice complexity
  - the project wants to own service reputation directly rather than delegate it
- `curated provider / partner hosts` would materially rise if:
  - users want convenience without making Prix itself the uptime/support operator
  - geography, jurisdiction, or provider choice matter
  - the project can maintain provider criteria and support-boundary labels more easily than it can run a first-party service
- `collectives` would materially rise if:
  - the project explicitly wants distributed stewardship, local/event hosts, or a plural-host product identity
  - not merely additional hosting capacity
- the hybrid `official hosted convenience + unpromoted private operators` would materially fall if:
  - users cannot reliably tell who supports a room
  - compatibility drift between official and unofficial hosts becomes a visible trust problem
  - unofficial hosts need promotion to be useful, which would push the system toward provider governance anyway

## What remains challengeable

`[open:reasoned:internal+external-direct]`

- whether `promoted provider / partner host` should be treated as a distinct named later branch in subsequent synthesis
- whether official first-party hosting ever becomes active priority instead of preserved optionality
- whether `unpromoted private operators` are enough, or whether some promoted-provider program becomes necessary before official hosting does
- what the minimum visible metadata is for:
  - host type
  - support owner
  - compatibility state
  - persistence/recovery expectation
- whether bounded event/showcase shells eventually strengthen `official hosted convenience` enough to overtake provider ecosystems

## Sensitivity implications

`[governing:reasoned:internal+external-direct]` Sensitivity may still treat the following as stable enough to protect:

- `trusted operators` remains the first hosting seam
- `official hosted convenience` is not the same branch as `collective governance`
- promoted-host language requires explicit support and trust boundaries

`[governing:reasoned:internal+external-direct]` Sensitivity should now additionally test for:

- prose that silently collapses `promoted provider / partner hosts` into `collectives`
- prose that silently collapses `promoted provider / partner hosts` into `official hosted convenience`
- prose that treats `official hosted convenience` as the only serious convenience-bearing later branch
- prose that treats the hybrid official-plus-private story as naturally clean without explicit support-owner clarity

`[governing:reasoned:internal+external-direct]` Recommended sensitivity classification after this challenge:

- `trusted operators` as first seam: `directly sensitivity-ready doctrine`
- `official first-party hosting` versus `provider ecosystem`: `bounded-open anti-hard-coding`
- `collective governance branch`: `preserve-only`
- `official hosted convenience as chosen later winner`: `reversal-sensitive`
- `hybrid official-plus-private is naturally clean`: `reversal-sensitive`

## What should remain out of sensitivity

`[governing:cited:internal]` The later sensitivity pass still should not force:

- a final winner between `official first-party hosting` and `provider ecosystem`
- a final naming scheme for the missing middle branch
- exact provider criteria, contracts, or SLA design
- exact host metadata schema or UI
- a roadmap commitment to run a first-party hosted service
- a public host directory or community-host program

## What later converged challenge synthesis must reconcile

`[assumed:reasoned:internal+external-direct]` Later converged challenge synthesis should reconcile this packet with:

- the money-family chunk:
  - `official first-party hosting` and `provider ecosystem` imply different revenue, support, and service-obligation stories
- the wrapper/community challenge:
  - bounded event/showcase pressure may strengthen `official first-party hosting` more than it strengthens provider ecosystems
- long-arc doctrine:
  - private-first posture still disfavors importing public/community obligations just because plural-host futures remain live
- residual hosting chunk C:
  - keep its useful `service identity` versus `governance identity` split
  - but insert a missing lighter `provider ecosystem` rival rather than treating `collectives` as the only serious non-official later branch
