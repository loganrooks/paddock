# 05 Post-Sensitivity Response Plan

## Diagnosis

The final sensitivity synthesis is useful as a gate artifact, but it is too weak as the headline outcome of this whole round.

The problem is not that the sensitivity pass found nothing.
The problem is that the converged output translated a large amount of substantive deliberation into a narrow `passes / patch lightly` posture.

That is too small a read of what the round actually produced.

The round now contains materially stronger mature-product doctrine about:

- wrapper families and first-shell ambiguity
- audience-right thresholds
- later money-family rivalry and promise grammar
- host-identity branching
- contribution/discovery posture
- event-memory and cadence layering

Stopping at a narrow interpretive patch would underuse that work and would leave too much future friction for Milestone 2 and later long-arc planning.

## Corrected standard

The correct standard after this round is not:

- `the docs pass`

It is:

- `the canon and roadmap now reflect the best mature-product doctrine we have actually earned`
- `the docs preserve the important later futures explicitly enough that Milestone 2 planning will not keep re-litigating the same ambiguities`
- `the docs do not silently hard-code or silently erase challengeable branches`

In other words:

- sensitivity was a gate
- not the endpoint

## Corrected next step

The next step should be a broader `canon uplift + milestone carry-forward + long-arc steering` response pass.

This is broader than the current `narrow canon-patch response` framing, but still disciplined:

- it should not choose final winners that remain genuinely open
- it should not widen Phase 01 execution scope
- it should not turn later branches into roadmap commitments

It should:

- make the earned doctrine more legible
- reduce future doc drift
- reduce Milestone 2 planning friction
- make preserve-only and reversal-sensitive branches more explicit where silence is doing too much work

## What this broader response should accomplish

### 1. Canon uplift, not mere cleanup

The response should not just clarify wording.
It should make the substantive conclusions of the round more durable across:

- `PROJECT.md`
- `LONG-ARC.md`
- `REQUIREMENTS.md`
- `ROADMAP.md`

### 2. Milestone 2 carry-forward

The response must explicitly help future Milestone 2 work by clarifying:

- which mature-product pressures already matter for M2 seam preservation
- which questions remain open but should stay visibly open
- which futures must not be quietly foreclosed by M2-oriented wording

### 3. Beyond-M2 long-arc carry-forward

The response must also explicitly help later doctrine, not just the next milestone, by clarifying:

- which later wrappers, hosting branches, memory layers, and contribution/discovery seams remain structurally important beyond Milestone 2
- which distinctions belong in `LONG-ARC.md` as durable doctrine rather than only in audit memory
- which futures should stay live even if Milestone 2 never activates them directly

### 4. Asymmetry relief

The response should fix the parts of canon where naming density still biases the future:

- `challenge` over-naming versus aftermath/recap under-naming
- `hosted` as owner-model shorthand
- `summary/replay` as stealth event-memory closure
- `reviewed / curated / unsupported` as unstable status vocabulary

### 5. Better explicit statusing

Some branches are currently preserved mostly by negative space.
That is too fragile.

The response should make status more explicit where useful:

- direct doctrine
- bounded-open branch
- preserve-only seam
- reversal-sensitive boundary

Not necessarily with those labels written verbatim into canon, but with wording that performs those distinctions more durably.

## File-by-file response emphasis

### `REQUIREMENTS.md`

This remains the first patch hotspot.

The response should:

- clarify that future wrapper, recurrence, and event-memory capabilities are illustrative and non-ranked
- make aftermath/recap, challenge, replay/review, and event-memory layering less asymmetrical
- keep `WRAP-*` and `RET-*` examples from masquerading as settled shell order or settled event-memory doctrine
- preserve future host/discovery/status distinctions without turning them into new ship gates

### `PROJECT.md`

This should carry more of the mature-product doctrine than it currently does.

The response should:

- widen future-wrapper examples so aftermath/recap is not semantically invisible
- keep low-burden wrapper order visibly open
- reflect that Milestone 2 pressure is not only content/cadence but also remote/private convenience, host identity, and layered memory
- avoid reading spectator/showcase examples as if they already outrank aftermath or challenge-result shells

### `LONG-ARC.md`

This should become the clearest durable doctrine surface for the round’s mature-product conclusions.

The response should:

- strengthen host-identity language so `hosted` does not collapse first-party, provider/partner, and private-operator branches
- preserve contribution/discovery status distinctions more explicitly
- keep `event`, `featured`, and `weekend` language from acting as automatic event-object proof
- preserve the challengeable rivalry between later money families without pretending a winner is chosen

### `ROADMAP.md`

This should do more than simply avoid drift.

The response should:

- make Phase 3 / Phase 5 / Phase 6 carry-forward notes better reflect the mature-product doctrine already earned
- keep M2-relevant seams alive explicitly
- keep recap/report, challenge-result, and event-memory layers separated
- keep host/convenience/service language capability-oriented rather than owner-model-choosing

### `01-CONTEXT.md`

This should still be treated carefully because it is a rerun input, not stable canon.

But if touched later, it should:

- preserve the broader doctrine without importing new execution scope
- keep non-decisions explicit
- avoid collapsing the current future-awareness vocabulary into a fake Phase 01 mandate

## Relationship to Phase 01 and Milestone 2

This response pass should be understood as serving three horizons at once:

- Phase 01 rerun quality
- Milestone 2 design friction reduction
- later long-arc doctrine preservation

It should not pretend those are the same thing.

For Phase 01:

- the job is mainly to keep the substrate and doctrine clean

For Milestone 2:

- the job is to keep later wrapper, hosting, memory, contribution, and money-family questions from being re-distorted by stale wording

For the longer arc:

- the job is to keep `LONG-ARC.md` and the other canon docs aligned so farther-wrapper, hosting, visibility, discovery, and memory futures are not preserved only by silence or audit-memory

## Recommended shape

Do not treat this as one tiny patch task.

Use a two-step response:

1. `canon uplift synthesis / patch proposal`
   - execution-ready
   - file-by-file
   - doctrine-aware
   - milestone-2-aware
   - long-arc-aware

2. `canon uplift execution`
   - patch the docs in sequence
   - then run a short consistency review

## Execution order

Recommended patch order:

1. `REQUIREMENTS.md`
2. `PROJECT.md`
3. `LONG-ARC.md`
4. `ROADMAP.md`
5. optional consistency touch on `01-CONTEXT.md` only if the rerun input genuinely needs it
6. consistency review across all touched docs

This is similar to the old Round 2B patch pattern, but broader in ambition because the current round produced more mature-product doctrine, not just seam clarifications.

## Final recommendation

Do not treat `05-sensitivity-converged-synthesis-output.md` as the satisfying conclusion of this work.

Treat it as the gate that permits the real response:

- a canon uplift
- with Milestone 2 carry-forward
- with longer-horizon long-arc carry-forward
- using the full mature-product doctrine earned by the remediation, residual, challenge, docket, and sensitivity rounds
- without pretending the still-open rankings are closed
