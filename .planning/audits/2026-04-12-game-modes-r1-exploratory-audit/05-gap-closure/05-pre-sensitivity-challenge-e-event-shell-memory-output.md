# 05 Pre-Sensitivity Challenge E: Event-Object Threshold And First Explicit Event Shell Output

## Research frame

- Mode: `hypothesis testing`
- Question:
  - does the current stronger-default framing over-read `event object threshold` as the answer to both `when event memory becomes real` and `which first explicit shell should exist first`?
- Scope:
  - stress-test the current threshold framing
  - compare `hosted-night recap`, `featured challenge result`, and `weekend board / scheduled event board`
  - keep direct external evidence separate from repo-local inference
  - narrow the first explicit shell without pretending the final event-memory UI is closed
- Non-goals:
  - not a final event-memory UI
  - not a final permanence policy
  - not a final cadence taxonomy
  - not a roadmap commitment to daily, weekend, or official-hosted programming
- Stop condition:
  - one challenge artifact exists that says whether the threshold framing survives, where it does not, and which first explicit shell is rough-shape-strong enough for later sensitivity to protect correctly

## Challenge framing

`[evidenced:cited:internal]` The residual synthesis currently leans toward three linked claims:

- `event memory` becomes real only after an `event object threshold`
- `daily/programmed challenge` should default to `editorial/programmed cadence`, not event memory
- the first explicit event shell is still unresolved between forms such as `hosted-night recap`, `featured challenge result`, or `weekend board`

`[assumed:reasoned:internal]` This packet treats that stronger-default framing as a hypothesis, not as doctrine. The main stress-test is whether the threshold framing is correct only for a later `event memory ledger`, but too strong if used to decide the first explicit shell of any kind.

## Target hypothesis

The current hypothesis under challenge is:

- a distinct `event memory` layer should not be named or protected until there is a real event object with bounded schedule, event-scoped participation, and event-scoped residue
- because of that, neither `daily/programmed challenge` nor `featured challenge result` should be treated as the first explicit event shell by default

## Why this hypothesis matters

`[evidenced:cited:internal]` This packet bears directly on:

- `RGR-05`
- supporting pressure from `RGR-01` and `RGR-06`
- `GCO-08D`
- `GCO-08E`

`[assumed:reasoned:internal]` If the threshold framing is under-challenged, the next sensitivity pass may protect the wrong seam:

- it could over-protect a later `weekend board / event board` idea and under-protect a nearer recap shell
- or it could flatten `featured challenge`, `hosted recap`, and `event memory` into one vague recurrence bucket again

## Gap justification

`[evidenced:cited:internal]` The residual chunk improved the question by tightening `event memory` into an `event object threshold`, but it intentionally left the first explicit shell unresolved. That means the current bundle still lacks an answer to:

- which explicit shell appears first in product-shape terms
- whether that first shell is already an eventized surface
- whether the threshold framing is doing naming discipline only, or actual product-ordering work

`[assumed:reasoned:internal]` This challenge packet exists because those are not the same question.

## What is already settled and not being relitigated

`[decided:cited:internal]` This packet does not reopen:

- the private-first, host-led, trusted-group product center
- layered memory doctrine:
  - player memory
  - room/group memory
  - event memory
  - content/library history
- the residual chunk E gain that `event memory` should not be used as a vague UI synonym
- the residual chunk A gain that `daily/programmed challenge` is not automatically a peer wrapper family

`[decided:reasoned:internal]` This packet is therefore not deciding whether Prix Guesser should build daily programming, official hosted weekends, or broad public event infrastructure. It is deciding how the first explicit shell should be named and protected before sensitivity.

## Strongest rival framing(s)

### Rival A: `Hosted-night recap` is the first explicit shell

- A bounded hosted session already creates a concrete object:
  - host
  - participant set
  - date/duration
  - results
  - recap-worthy residue
- Under this framing, the first explicit shell is a `session recap / hosted-night report` rather than a true event board.
- `Event memory` can still remain later and threshold-gated.

### Rival B: `Featured challenge result` is explicit enough to count first

- A scheduled or deadline-bound challenge result page can create a visible, revisitable object before any heavier event system exists.
- Under this framing, `daily/programmed challenge` is not just editorial cadence; it is the first concrete event-like shell.

### Rival C: `Weekend board / scheduled event board` should be first because it is the cleanest true event object

- If event memory should only exist once an event object exists, the first explicit shell should also wait for a real scheduled board with event-scoped results, proofs, or rewards.
- This is the strongest version of the current threshold framing.

  - the strongest reframing is that `event object threshold` may be valid for a distinct `event memory ledger` while still being too strict for the first explicit post-session shell

## Assumptions surfaced

- `Hosted-night recap` is only useful if the product can point to a real bounded session object, not just a generic scoreboard screen.
- `Featured challenge result` is only a serious rival if it creates more than ordinary async reuse and can be revisited as a named result surface.
- `Weekend board` is only comparable if its heavier schedule/eligibility/proof burden is made explicit rather than smuggled in under the word `featured`.
- Comparable products are being used for structural translation, not as direct product prescriptions for Prix Guesser.

## Negative-case / counterexample note

`[evidenced:cited:external-direct]` Three counterexamples matter here:

- `Kahoot` shows a live hosted session can end in a concrete report object with summary, leaderboard, date, duration, host identity, and shareable podium. That weakens the strongest reading of `nothing explicit should exist before a true event object`.
- `GeoGuessr Daily Challenge` and `Chess Daily Puzzle` show that timed, repeated, site-level result surfaces can be concrete and revisitable while still reading more like editorial cadence than true event memory.
- `GeoGuessr Events`, `GeoGuessr Tournaments`, `Strava` event matching/insights, and `Discord Scheduled Events` show that once a product is really talking about an `event`, it usually adds schedule, participation boundary, proof, reminders, or rewards that are qualitatively heavier than a recap or featured result page.

## Evidence that strengthens the current hypothesis

`[evidenced:cited:external-direct]` The current threshold framing is strongly supported in one specific sense:

- `GeoGuessr Events` are for a specific time frame on custom maps/settings and award top-three medals.
- `GeoGuessr Tournaments` happen on a fixed weekly schedule, tier players by ELO, and award trophies.
- `Chess.com` exposes upcoming, joined, completed, and hosted tournaments separately from ordinary stats.
- `Strava Activity Event Match` links an activity to an attended event only when time and location criteria match, and `Club Event Insights` compares attendance against previous club events.
- `Discord Scheduled Events` add explicit event creation, start/cancel flows, event links, interested-state reminders, and visibility rules.

`[inference:reasoned]` Taken together, those examples support:

- `event memory` is not just a vivid recap
- real event objects usually have:
  - bounded schedule or start time
  - event-scoped participation or attendance logic
  - event-specific residue such as trophies, medals, proof, comparisons, or notifications
- a themed weekend board without those traits is not yet strong enough to be called `event memory`

`[evidenced:cited:external-direct]` The evidence also supports the local claim that `daily/programmed challenge` is editorial/programmed by default:

- `GeoGuessr Daily Challenge` is daily world competition, but it is still presented separately from Events and Tournaments
- `Chess Daily Puzzle` starts daily at midnight Pacific and supports revisiting older puzzles by date, while tournament history is separately tracked

## Evidence that weakens or complicates it

`[evidenced:cited:external-direct]` The current framing weakens when it tries to do first-shell ordering work by itself:

- `Kahoot` reports show that a live hosted session already creates a concrete post-session object:
  - the report can show summary, participants, questions, feedback, session duration, date, host, detailed leaderboard, and podium sharing
  - this is more than generic room folklore
- `GeoGuessr` invite-only challenges and challenge result views show that bounded challenge objects can have an explicit results surface even before any higher-order event system exists
- `GeoGuessr Live Challenges` show a live friend session with leaderboard/progress inside the run without turning that into a weekly event board

`[inference:reasoned]` This means:

- the threshold framing is correct for the phrase `event memory`
- but it is too coarse if interpreted as `the first explicit shell must already be a true event object`

`[evidenced:cited:external-direct]` The threshold framing also weakens if it lets `weekend board` dominate too early:

- every strong true-event example carries heavier burdens:
  - tiers/trophies
  - schedule/start state
  - RSVP/Interested reminders
  - permission controls
  - comparative event history
- those burdens are materially farther from Prix Guesser's private-first center than a hosted-session recap is

## Comparative verdict

`[assumed:reasoned]` The current hypothesis survives only in narrowed form.

What survives:

- `event memory` should still require an `event object threshold`
- `daily/programmed challenge` should still default to `editorial/programmed cadence`, not automatic event memory

What weakens:

- the threshold framing should not by itself decide the first explicit shell
- the first explicit shell should narrow toward `hosted-night recap / session report`, not `weekend board`

`[assumed:reasoned]` The strongest challenge-round answer is therefore:

- first explicit shell:
  - `hosted-night recap / session report`
- strongest secondary rival:
  - `featured challenge result`
- first true event-memory shell later:
  - `weekend board / scheduled event board`, but only once genuine event-object semantics are present

`[assumed:reasoned]` In other words:

- `event object threshold` is good doctrine for the phrase `event memory`
- the first explicit shell can arrive earlier as a session-bound recap object without yet counting as full `event memory`
- it is not the whole answer to `what explicit shell appears first`

## What can close now

- The bundle can now distinguish `first explicit shell` from `first true event-memory shell`.
- `Hosted-night recap / session report` is the strongest first explicit shell for later sensitivity to protect, but it should be protected as session-bound recap residue rather than as already-eventized memory.
- `Featured challenge result` should be carried forward as an editorial/challenge-result rival, not as the default event-memory answer.
- `Weekend board / scheduled event board` should be treated as the strongest later true-event shell, not the first explicit shell by default.

## What would falsify or materially re-rank the hypothesis

- If playtesting shows the real repeat-return center is mostly async remote challenge reuse rather than hosted-session recurrence, `featured challenge result` could outrank `hosted-night recap`.
- If Prix deliberately chooses official scheduled programming with reminders, event-specific participation, and board-worthy proof much earlier than the current posture suggests, `weekend board` could become the first explicit shell.
- If the product cannot point to a stable hosted-session object beyond a transient room summary, `hosted-night recap` loses force and the first-shell question reopens.

## What remains challengeable

- the exact boundary between `room recap`, `hosted-night recap`, and a named recurring-group surface
- whether a `featured challenge result` deserves archive treatment before any official weekend/event layer exists
- whether the first explicit shell should be visible only to participants, share-by-link, or selectively outward-facing
- the exact trigger that upgrades a themed `race weekend` surface from spotlight or featured challenge into a true event object
- permanence depth, navigation model, and exposure rules for any later event-memory ledger

## What must stay open

- exact shell naming
- exact permanence/retention depth
- exact cadence labels such as `daily`, `featured`, `weekend`, or `event`
- whether early hosted recaps remain participant-bounded or become selectively visible
- whether `featured challenge result` becomes a meaningful middle shell before any true event board

## Sensitivity implications

`[assumed:reasoned]` A later sensitivity pass may now assume:

- `event memory` requires a true event object
- `first explicit shell` and `first true event-memory shell` are not the same thing
- the most plausible first explicit shell is `hosted-night recap / session report`
- `featured challenge result`, `daily/programmed challenge`, and `weekend board` are not interchangeable

`[assumed:reasoned]` A later sensitivity pass still may not assume:

- a final event-memory UI
- a final permanence or archive policy
- that `weekend board` is first by default
- that `featured challenge result` is already the chosen middle shell
- that any named `race weekend` surface is automatically a true event object

## What should remain out of sensitivity

- exact report/board screen design
- exact trophy, medal, RSVP, or notification mechanics
- exact public/private visibility rules
- exact content-operations commitment for daily or weekend programming
- exact room/group/event promotion ladder

## What later converged challenge synthesis must reconcile

- this packet's `hosted-night recap first` narrowing with packet A's wrapper-ordering judgments
- this packet's `featured challenge result` as a real secondary rival with the content/cadence burden analysis from the recurrence lane
- this packet's `weekend board later` judgment with any hosting-branch language that starts implying official scheduled operations too early
- this packet's `event memory threshold survives` judgment with the memory-ledger doctrine from chunk E so recap, challenge result, and event memory do not collapse together again

## Hypothesis status

`weakened but survives in bounded form`

- survives as doctrine for `event memory`
- weakens as doctrine for `first explicit shell`
