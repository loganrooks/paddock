# 05 Sensitivity Docket C2: Collectives, Plural Hosts, And Hybrid Risks

## Docket framing

- Mode: `feature-to-doc translation`
- Classification: `initial architecture research/planning`
- Governing question:
  how should the core planning docs preserve `collective / mirror governance` as a real later seam while also refusing the shortcut claim that `official hosted convenience + private hosts` is already a naturally coherent plural-host answer?
- Non-goals:
  - not choosing a later hosting winner
  - not re-running `first-party hosted convenience` versus `provider / partner host`; that belongs to `C1`
  - not defining host-program criteria, covenant terms, or host-directory mechanics
  - not turning preserve-only plural-host seams into roadmap commitments

## Target feature pressure

- `collective / mirror governance` remains `preserve-only`, not dead.
- `plural-host future` must stay distinguishable from:
  - `provider / partner host`
  - `official first-party hosted convenience`
  - `unpromoted private operators`
- `hybrid official-plus-private hosting is naturally clean` remains `reversal-sensitive`.
- the word `hybrid` already exists in canon for play topology; sensitivity must prevent that from being misread as host-ecology doctrine.

## Current gate classification

- `collective / mirror governance` as a later hosting identity: `preserve-only`
- `plural-host seam must remain visibly preserved`: `direct doctrine about non-foreclosure`
- `collective governance` versus `provider ecosystem` versus `official service` are distinct identities: `direct doctrine about distinction`
- `hybrid official-plus-private hosting is naturally clean`: `reversal-sensitive`
- whether any governed plural-host branch ever rises above preserve-only: still `open`, not sensitivity-closable

## Current survivor and strongest rival(s)

- The surviving logic is narrow but real:
  `collective / mirror governance` survived the challenge round as a preserved later seam because it solves a different problem from both `official hosted convenience` and `provider / partner hosts`.
- The seam is weak in ranking terms but strong in non-foreclosure terms:
  it is not the current default, but it is not honestly classifiable as dead.
- The strongest practical rival pressure against this seam is not `collectives lose to official hosting`.
  It is the tidier story that later plurality is already covered by:
  - one official hosted surface
  - plus unsupported private operators
  - and maybe promoted providers
- The strongest reversal risk is therefore the hybrid story itself:
  if docs imply that official and non-official hosts naturally coexist cleanly, the heavier governance identity disappears without ever being explicitly rejected.

## Why this pressure matters

- The canon is intentionally high-level about later hosting.
  That makes preserve-only seams easy to erase through omission.
- The challenge round tightened two points at once:
  - `collective governance` is heavier than provider ecosystems and should not be collapsed into them
  - `official hosted convenience + unpromoted private operators` is plausible but operationally fragile, not a clean default
- `PROJECT.md` already uses `hybrid` for session topology.
  Without a docket, later readers can slide from `hybrid sessions` to `hybrid hosting` as if those are the same kind of preserved future.
- `LONG-ARC.md` correctly defers broad community-host governance today.
  But a deferred burden can silently turn into a dead branch if the docs never restate that the seam remains intentionally preserved.
- `REQUIREMENTS.md` is seam-oriented and host-identity-neutral now.
  That neutrality is safe only if later readers remember that host plurality would require explicit host-type, support-owner, compatibility, and governance language before activation.

## Per-doc implication map

### [PROJECT.md](/home/rookslog/workspace/projects/prix-guesser/.planning/PROJECT.md)

- Safe:
  the document may keep the current center at private social play across couch, remote, and hybrid sessions, and may preserve later remote durability or expansion pressure at a high level.
- Overcommit risk:
  if `hybrid` language or later remote-hosting language is read as proof that mixed official and non-official host ecologies are already coherent enough to treat as settled.
- Silent foreclosure risk:
  if the future story leaves room only for:
  - current private operators
  - later official hosted convenience
  while never acknowledging that a governed plural-host identity remains a preserved but heavier future.
- What must remain explicit here:
  `hybrid sessions` means play topology, not hosting doctrine.
  Community-host or collective governance remains a preserved later seam only if the project deliberately accepts stronger governance burdens.

### [LONG-ARC.md](/home/rookslog/workspace/projects/prix-guesser/.planning/LONG-ARC.md)

- Safe:
  the document may preserve `self-hostable authoritative rooms`, separate hosting from support/access/service obligation, and explicitly defer `broad community-host governance` for the current posture.
- Overcommit risk:
  if `modest hosted operation` or the hosting ladder is read as proof that one official service plus optional private operators is the resolved mature shape.
- Silent foreclosure risk:
  if community-host governance appears only as a current deferral and never as a still-preserved later identity.
  That would quietly collapse plural-host futures into lighter provider or official-service branches.
- What must remain explicit here:
  `collective / mirror governance` is a different later identity from both `provider ecosystem` and `official hosted convenience`.
  If it ever becomes active, it would require explicit standards, review, compatibility discipline, shutdown/contact posture, and support-owner clarity.
  A mixed official-plus-private ecology is not assumed clean by default.

### [REQUIREMENTS.md](/home/rookslog/workspace/projects/prix-guesser/.planning/REQUIREMENTS.md)

- Safe:
  the current `DEPLOY-*`, `DIST-*`, `SEAM-*`, and `DEF-*` surfaces may stay host-identity-neutral and private-first.
  The current deferrals around public trust, moderation, and service obligation are compatible with preserve-only plural-host seams.
- Overcommit risk:
  if future requirements add `community hosting`, `official hosted`, or `partner-host` language as if one mixed ecosystem is already coherent, without separating host type, support owner, and governance burden.
- Silent foreclosure risk:
  if future requirement growth preserves only:
  - official hosted convenience
  - unsupported private hosting
  while never leaving room for a governed plural-host branch to be named later.
- What must remain explicit here:
  deferral is not death.
  If later host plurality becomes a requirement family, the doc will need to distinguish:
  - official service
  - promoted provider hosts
  - governed collectives / mirrors
  - unsupported private operators

## What each doc may safely imply

- [PROJECT.md](/home/rookslog/workspace/projects/prix-guesser/.planning/PROJECT.md) may safely imply a private-first product center, later remote/private durability pressure, and mixed play topologies without deciding a plural-host doctrine.
- [LONG-ARC.md](/home/rookslog/workspace/projects/prix-guesser/.planning/LONG-ARC.md) may safely imply that community-host governance is deferred because it carries heavier obligations, not because it has been disproven or banned.
- [REQUIREMENTS.md](/home/rookslog/workspace/projects/prix-guesser/.planning/REQUIREMENTS.md) may safely imply host-capability seams and explicit deferrals without ranking later plural-host identities.
- All three docs may safely imply that later plurality is possible only if host identity, support ownership, and trust boundaries become explicit.

## What each doc must not imply

- that `collective / mirror governance` is dead just because it is preserve-only
- that `provider / partner host`, `collective / mirror governance`, and `unsupported private operator` are interchangeable labels for the same future
- that `official hosted convenience + private hosts` is already a naturally legible, low-risk hybrid
- that the current use of `hybrid` for couch/remote play topology says anything about later host-ecology clarity
- that current deferrals around public/community burden mean plural-host governance can be forgotten safely

## What must remain explicit

- `collective / mirror governance` remains a preserved later seam, not an active default branch.
- `provider ecosystem`, `official hosted convenience`, `governed collectives / mirrors`, and `unsupported private operators` are distinct host identities.
- Governed plural-host futures are heavier because they imply standards, review, compatibility discipline, contact/shutdown posture, and visible trust metadata.
- `hybrid official-plus-private hosting is naturally clean` remains reversal-sensitive until support-owner and compatibility boundaries are explicit.
- The current canon defers public/community obligations now without foreclosing a later plural-host branch if the project deliberately chooses that burden.

## Semantic drift watchpoints

- `hybrid`
  do not blur `hybrid session topology` with `hybrid hosting ecology`.
- `collective`, `mirror`, `community host`
  do not use these as loose synonyms for `provider / partner host`.
- `provider`, `partner host`, `promoted host`
  do not let these drift into `governed collective` merely because both involve plurality.
- `hosted`
  do not let generic hosted language imply that mixed official and non-official ecosystems are already trust-clear.
- `deferred`
  do not let it silently become `dead`.
- `community governance`
  do not use it as shorthand for capacity scaling or convenience outsourcing.

## Sensitivity lane routing

- `Lane I: canon doctrine`
  primary consumer for [PROJECT.md](/home/rookslog/workspace/projects/prix-guesser/.planning/PROJECT.md), [LONG-ARC.md](/home/rookslog/workspace/projects/prix-guesser/.planning/LONG-ARC.md), and [REQUIREMENTS.md](/home/rookslog/workspace/projects/prix-guesser/.planning/REQUIREMENTS.md).
  Protect:
  - preserve-only plural-host seam visibility
  - distinction between governed collectives and lighter host plurality
  - the rule that `hybrid` wording must not smuggle in host-clarity claims
- `Lane III: preserve-only and reversal-sensitive futures`
  primary doctrinal owner for this docket.
  Test specifically for:
  - prose that kills `collective / mirror governance` by omission
  - prose that upgrades `official + private` hybrid language into calm doctrine
- `Lane II: roadmap and rerun`
  secondary only.
  Use this docket if roadmap or rerun artifacts begin naming plural-host futures; otherwise do not widen scope just to force a roadmap stance.
- `Lane IV: inquiry debt and anti-hard-coding`
  secondary only.
  Use this docket when prose starts turning repeated deferral language into hidden closure.

## What remains open after this docket

- whether any governed plural-host branch ever earns elevation above preserve-only
- what the minimum visible metadata is if plural hosts are ever activated:
  - host type
  - support owner
  - compatibility state
  - shutdown/contact posture
- whether a later `provider / partner host` program absorbs the practical plurality need before collective governance matters
- whether the hybrid `official hosted convenience + unsupported private hosts` story can ever become legible enough to survive, or whether it collapses into either:
  - a clearer provider program
  - a clearer official-service posture
  - or a deliberately governed plural-host branch
- what canonical vocabulary should eventually be used if the project ever wants to name plural-host governance without importing public-social-network baggage
