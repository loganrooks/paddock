# 05 Sensitivity Docket B2: Service Promises And Paid Participation Output

## Docket framing

- Mode: `synthesis`
- Classification: `initial architecture research/planning`
- Question:
  how should the live planning docs preserve the current doctrine that `paid guaranteed participation / priority / reserved-slot` remains reversal-sensitive, while preventing supporter-benefit language from quietly reintroducing booking, fairness, or service-promise semantics?
- Scope:
  - service-bearing promise grammar
  - supporter-benefit classes as branch selectors
  - paid-participation reversal pressure
  - challenge-shell and event-shell wording where it could be misread as admission doctrine
  - per-doc implications for the core canon and the most directly affected downstream planning surfaces
- Non-goals:
  - exact prices
  - exact perk lists
  - choosing a later money-family winner between `editorial/content` and `hosted convenience`
  - designing a final event or ticket model
  - writing canon patches in this docket
- Stop condition:
  each affected doc has a clear safe/unsafe implication boundary, and the later sensitivity lanes can test drift without re-running the money/service challenge bundle
- Entry point:
  - `05-sensitivity-docket-b2-service-promises-paid-participation-task-spec.md`
  - `05-pre-sensitivity-challenge-converged-synthesis-output.md`
  - `05-pre-sensitivity-challenge-b-money-service-output.md`
- Branches pursued:
  - challenge-round conclusions about `paid guaranteed participation`
  - residual and remediation findings on supporter benefits as branch selectors
  - current canon and planning prose around support, access, service obligation, challenge shells, and room lifecycle
- Branches deferred:
  - exact supporter-benefit catalog design
  - exact later event shell that would count as a true booking/ticket posture
  - final later monetization ranking

## Target feature pressure

- Primary pressure:
  - `paid guaranteed participation / priority / reserved-slot` still sits outside the ordinary later-money ladder and remains reversal-sensitive.
  - supporter benefits can quietly smuggle service or fairness promises back in.
  - the highest-risk soft phrasings are `premium access`, `member-only game nights`, `supporter challenge access`, `faster support`, `reserved seats`, and `priority` language.
- Direct evidence:
  - the converged challenge synthesis keeps `paid guaranteed participation`, `priority`, `reserved slots`, and similar language in the `reversal-sensitive` bucket.
  - the challenge B packet sharpens the boundary: `paid guaranteed participation` reads like booking/service semantics rather than ordinary support or content language.
  - residual chunk B concludes that supporter benefits are branch selectors, not harmless parameter detail; `reserved seats`, `queue priority`, and `faster support` map directly to the paid-participation/service branch.
- Inference:
  - this docket is not about whether later money families remain live. B1 owns the family rivalry.
  - B2 exists because benefit language can short-circuit B1 by choosing a service identity or booking posture before the docs ever say they did.
  - challenge-shell and event-shell terms are especially exposed because they can sound like harmless wrapper vocabulary while quietly importing admission or entitlement meaning.

## Current gate classification

| Surface | Current class | Why |
| --- | --- | --- |
| `optional support first` with recognition-level benefits | `direct doctrine` | already supported by `LONG-ARC.md` support/access/service separation |
| `support-plus-beta` | `bounded-open` | narrow transitional instrument only; still expectation-heavy and not a default story |
| supporter perks that buy convenience or service response | `bounded-open` with high drift risk | they quietly select `hosted convenience` and a stronger service posture |
| supporter perks that buy premium packs, drops, or programming | `bounded-open` | they select `editorial/content`, not generic support |
| `paid guaranteed participation / priority / reserved-slot` | `reversal-sensitive` | these are booking/service semantics, not normal later-money language |
| later explicit paid event shell | `open` but not live | challenge-round nuance leaves this reopenable only through an explicit later doctrine shift, not through soft perk wording |

## Current survivor and strongest rival(s)

- Current survivor:
  `optional support first` remains the live early posture, with `queue / capacity honesty` before monetized access pressure and with supporter benefits staying recognition-level rather than operational.
- Strongest rival A:
  supporter perks that buy easier official room start, persistent remote access, backups, always-on availability, account-linked convenience, or faster issue response. These do not remain neutral; they select a service-bearing `hosted convenience` branch.
- Strongest rival B:
  supporter perks that buy premium packs, recurring drops, event-programming access, or subscriber-only authored material. These select `editorial/content`, not pure support.
- Strongest rival C:
  `reserved seats`, `priority`, `member-only game nights`, `supporter challenge access`, or similar wording that makes money buy dependable participation itself. This is the main reversal-sensitive danger.
- Challenge-round nuance to preserve:
  the current doctrine does not prove participant-paid access is metaphysically impossible forever. It says that under the current private-first posture it is outside the ordinary ladder, and any later return would be an explicit move into event/service identity with stronger fairness, support, and accountability obligations.

## Assumptions surfaced

- `[assumed:reasoned]` Benefit wording is load-bearing architecture pressure, not copy polish.
  If this is false, B2 is unnecessary. The challenge and residual bundle says it is true.
- `[assumed:reasoned]` The current canon wants low-obligation private-first support, not customer-service promises.
  If the product deliberately changes that doctrine later, the outcome of this docket must be reopened rather than treated as permanent truth.
- `[assumed:reasoned]` Terms like `challenge`, `event`, and `seat claim` can drift from structural meaning into economic meaning unless the lanes test them explicitly.

## Why this pressure matters

- B1 keeps the later money-family rivalry open. B2 prevents support language from secretly deciding that rivalry through service-bearing perks or admission promises.
- The current canon already distinguishes visibility, hosting, support, access, cadence, and memory layers. If service promises leak back in, those distinctions stop being neutral structure and start becoming undeclared entitlement policy.
- The drift risk is asymmetric:
  a small phrase like `priority`, `supporter challenge`, or `member-only hosted night` can import queue legitimacy, customer-service expectations, refund/fairness questions, and stronger uptime assumptions much faster than any roadmap or requirements patch would.
- Challenge-round nuance matters here:
  the project now treats `first explicit shell` and `true event-object shell` as different questions. If those get collapsed, someone can use a recap/challenge shell as soft justification for paid admission long before the product has chosen an event-service identity.

## Per-doc implication map

### `PROJECT.md`

Current read:
already aligned. The strongest current guardrail is the explicit statement that trust and service assumptions remain modest and include `no paid guaranteed access promise`.

Safe:

- keep `private-only`, `trusted groups`, `browser-first`, layered visibility, and layered cadence/memory language
- keep challenge/share/spectator wrappers visible as later shells without implying admission rights
- keep the current posture that there is no paid guaranteed access promise now

Would overcommit:

- supporter or member language that buys priority room access, reserved challenge participation, guaranteed spots in hosted nights, or faster fixes
- soft `premium access` phrasing that collapses support and participation rights

Would silently foreclose:

- rewriting project posture as if paid participation can never exist under any later deliberate service/event identity

Must remain explicit:

- later challenge/event shells are wrapper or program surfaces first, not ticket doctrine by default
- any move from support into participant-paid access would be a deliberate product-doctrine change, not a natural extension of current supporter language

### `LONG-ARC.md`

Current read:
this is the strongest existing guardrail. It already separates support, access, and service obligation, and already says paid guaranteed access is later-stage rather than current doctrine.

Safe:

- preserve `support`, `access`, and `service obligation` as separate axes
- preserve the current claim that optional support can exist without changing room access or service promises
- preserve the claim that challenge links, showcase surfaces, and public read surfaces are not the same decision as stranger participation or stronger service obligation

Would overcommit:

- `membership`, `premium access`, or service language that lets money alter participation, queue position, support response, or uptime expectations while still pretending the doctrine is unchanged

Would silently foreclose:

- hardening the current deferral into a permanent impossibility, which would erase the challenge-round nuance that a later true event/service posture could reopen the question explicitly

Must remain explicit:

- service-bearing branches are separate from visibility transitions
- if a later event/ticket posture is ever chosen, it would mean intentionally accepting stronger accountability, fairness, and support obligations

### `REQUIREMENTS.md`

Current read:
aligned, but future wrapper and retention requirements need to stay monetization-neutral. `WRAP-01`, `RET-01`, and `RET-04` create shell vocabulary that could be misread later if lanes do not guard it.

Safe:

- keep `WRAP-01`, `RET-01`, `RET-04`, and later shells neutral about monetization
- keep `DEF-02` and `DEF-03` as the explicit brakes on service-obligation and paid-guaranteed-access drift
- keep `SEAM-05`, `SEAM-06`, and `SEAM-08` protecting separation among wrapper access, event containers, and layered histories

Would overcommit:

- adding or implying member-only challenge access, supporter queues, reserved seats, faster support response, or premium participation rights inside wrapper, retention, or distribution requirements

Would silently foreclose:

- wording future wrappers or event containers so narrowly that no later explicit event/service requirement could ever be introduced deliberately

Must remain explicit:

- current requirements preserve future shells, not their business model
- any future access-selling requirement would be a new later doctrine choice, not a hidden interpretation of `WRAP-01`, `RET-01`, or `RET-04`

### `ROADMAP.md`

Current read:
mostly aligned. The main watchpoints are `modest service obligation`, `seat claim`, later challenge surfaces, and any future tendency to treat private-host durability as premium-service doctrine.

Safe:

- Phase 3, 4, and 7 may talk about modest service obligation, private-host durability, join/rejoin continuity, and lifecycle correctness as operator/runtime concerns rather than supporter entitlements
- `seat claim` is safe only as temporary in-room identity or state ownership during a live session

Would overcommit:

- reserved slots, supporter entry priority, member-only challenges, premium remote access as a default phase assumption, or faster issue-response promises

Would silently foreclose:

- planning later phases as if explicit event/service shells can never exist; this docket should stop accidental promises, not write `never` into the roadmap

Must remain explicit:

- `seat claim` does not mean advance reservation or paid admission
- `challenge`, `share-by-link`, and `audience-only entry` are visibility-right surfaces, not price tiers

### `01-CONTEXT.md`

Current read:
aligned. The file already says there is no public discovery, moderation, uptime, or paid-access obligation in the current posture.

Safe:

- preserve the current `no paid-access obligation` posture
- preserve later wrapper reuse and async challenge preservation as substrate notes, not access-policy commitments

Would overcommit:

- importing membership, supporter-benefit, premium-access, or paid challenge/event concepts into a content-contract phase

Would silently foreclose:

- using a Phase 1 context file to settle later service/event questions globally instead of leaving them to later doctrine work

Must remain explicit:

- later wrappers reuse the substrate; they do not carry implied access-selling rights just because the substrate supports them

## What each doc may safely imply

- `PROJECT.md` and `LONG-ARC.md` may safely imply voluntary support, low-obligation private operation, and later wrapper visibility without selling participation.
- `REQUIREMENTS.md` may safely imply future challenge, replay, recurrence, and event-adjacent shells as structural possibilities only, not monetized entitlements.
- `ROADMAP.md` and `01-CONTEXT.md` may safely imply operator continuity, join/rejoin lifecycle, room-state ownership, and later wrapper reuse as technical/product seams rather than service contracts.
- any doc may safely imply that if scarcity ever becomes real, `queue / capacity honesty` comes before monetized priority.

## What each doc must not imply

- money buys guaranteed room participation, queue priority, reserved slots, or `member-only` hosted nights/challenge entry
- supporters get faster issue response, better uptime, or stronger host/service guarantees than ordinary participants under current doctrine
- `premium` or `membership` is an acceptable umbrella for mixed support, content, convenience, and participation rights
- challenge/share-by-link/event wording already proves a ticketable or subscriber-only shell
- `seat claim` means advance reservation rather than transient room-state identity
- `paid guaranteed access` is already a normal later-money option inside the current doctrine

## What must remain explicit

- `support`, `access`, and `service obligation` stay separate
- `queue / capacity honesty` is not monetization
- supporter benefits are branch selectors:
  - recognition and thanks map to `support`
  - remote access, backups, always-on convenience, or faster support map to `hosted convenience`
  - premium packs, recurring drops, or programming access map to `editorial/content`
  - reserved seats, queue priority, faster response, or dependable admission map to `paid participation / booking-service`
- `paid guaranteed participation` stays outside the ordinary later-money ladder under current doctrine
- a later true paid-event or booking posture would require an explicit doctrine reversal plus an explicit event/service identity, not just softened perk wording
- `challenge`, `recap`, and `event object` remain separate questions

## Semantic drift watchpoints

| Term | Safe current reading | Drift to flag |
| --- | --- | --- |
| `support` / `supporter` | voluntary backing with no access effect | `supporter access`, `supporter queue`, `supporter priority`, or implied response guarantees |
| `premium` | avoid unless immediately unpacked into a specific family | umbrella term that hides whether the doc means content, convenience, or participation rights |
| `membership` | avoid in doctrine unless recurring benefit accountability is actually intended | makes support sound like entitlement-bearing tiers |
| `priority` / `reserved slot` / `guaranteed participation` | currently safe only as reversal-warning language | any positive use imports booking/service semantics |
| `seat claim` | transient in-room state ownership | reservation, admission, or entitlement semantics |
| `challenge` / `hosted night` / `event` | wrapper, cadence, or event-object vocabulary that must stay distinct | `member-only challenge`, `ticketed hosted night`, or `featured event` being used as proof that paid admission is natural |
| `remote access` / `backups` / `always on` / `faster support` | service-bearing convenience promises | hiding a hosted-convenience branch inside generic supporter benefits |
| `exclusive pack` / `subscriber drop` / `programming access` | explicit `editorial/content` branch language | mislabeling content/program access as pure support or generic membership |
| `beta` / `early access` | bounded learning lane only if entry, exit, and current-state limits are explicit | disguised durable membership or soft priority doctrine |

## Sensitivity lane routing

- `Lane I: Canon Doctrine`
  - consume this docket against `PROJECT.md`, `LONG-ARC.md`, and `REQUIREMENTS.md`
  - confirm the docs preserve support/access/service separation and keep wrapper/retention surfaces monetization-neutral
  - verify that `DEF-03` stays a deferral boundary rather than drifting toward either soft permission or permanent metaphysical ban
- `Lane III: Preserve-Only And Reversal-Sensitive Futures`
  - consume this docket against `ROADMAP.md` and `01-CONTEXT.md`
  - treat `seat claim`, challenge/event-shell language, premium/membership drift, and faster-support drift as the main watchpoints
  - classify participant-paid access language as reversal-sensitive rather than harmless future-awareness
- Converged sensitivity synthesis:
  - reconcile B2 with B1 so the later money-family rivalry stays open while the service-promise guardrail stays hard
  - do not let B1's preserved rivalry become a justification for soft paid-participation language

## What remains open after this docket

- the exact recognition-level supporter benefits that stay safely non-operational
- whether any bounded `support-plus-beta` lane is ever worth running for this project
- the precise later trigger where a true event object plus deliberate service identity would reopen participant-paid access
- the exact future wording for `editorial/content` or `hosted convenience` benefits if either family is ever promoted explicitly
- how later recap/event-memory shells from the E dockets might interact with any future paid-entry idea without collapsing into ticket logic prematurely
