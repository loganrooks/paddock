# 05 Remediation Converged Synthesis Output

## Research Frame

- Mode: `synthesis`
- Classification: `initial architecture research/planning`
- Question: after the five remediation packets, what now counts as closure-grade mature-product doctrine, what remains only preferred, what is still open, and what is and is not ready for the post-closure sensitivity pass?
- Scope:
  - reconcile packet outputs against `GCO-10` and `GCO-11`
  - preserve the repo's already-settled private-first and seam-preserving doctrine
  - produce one integrated maturity answer in wrapper, promise, hosting, contribution, and recurrence terms
- Non-goals:
  - not a canon patch
  - not a roadmap reprioritization
  - not a final ranking of every later branch

## Integrated Decision Structure

### 1. Wrapper Shells And Audience Rights

- `settled doctrine`: there is no single universal first post-private wrapper. `showcase aftermath`, `share-by-link / challenge`, `bounded live audience`, and `ambient community layer` are different shell families with different burden profiles. Audience rights should be modeled as capability bundles, not one ladder. `ambient community layer` now means a persistent, discoverable, moderation-bearing service branch and should no longer be used as a vague catch-all.
- `preferred but challengeable branch`: carry forward a split low-burden answer. `showcase aftermath` and `share-by-link / challenge` are the two strongest first extensions of the private-first core, while `bounded live audience` is the first credible live public-adjacent shell for the bounded-event archetype.
- `unresolved branch`: if one wrapper must be named first across all archetypes, that ranking is still open. It is also still open whether a daily/programmed challenge belongs in the same branch family as friend-to-friend challenge links, which audience-right bundles should appear first, and whether live audience is earned before stronger solo/async reuse is proven.
- `empirical trigger`: promote `showcase aftermath` if groups already revisit standings, reveals, or ad hoc screenshots; promote `share-by-link / challenge` if time-shifted play and absent-friend rivalry matter more than watchability; promote `bounded live audience` if hosted-event demand, reveal clarity, and audience moderation capacity all become real.
- `possible later spike candidate`: `mixed spectator-participant capability bundles`, but only if passive live audience proves too thin once a bounded audience shell exists.
- `sensitivity-ready now`: yes for the doctrine split, the audience-capability model, and the boundary that keeps `ambient community layer` distinctly later and heavier.
- `still not sensitivity-ready`: no for a global first-wrapper ranking, first audience bundle, or an active commitment to an ambient community roadmap.

### 2. Promise Grammar And Economic Ladders

- `settled doctrine`: the honest early posture is `optional support first`, not `support-plus-access`. Scarcity should first be handled through queue/capacity honesty, not monetized priority. The real posture-change line is still `dependable paid participation`, because that turns support into service obligation.
- `preferred but challengeable branch`: preserve two later money families without naming a winner:
  - `hosted convenience`
  - `editorial programming / content`
  `support-plus-beta` remains alive only as a narrow transitional instrument for bounded learning surfaces.
- `unresolved branch`: which later family becomes stronger after more mature-product synthesis remains open. It is also open whether `support-plus-beta` is ever worth using at all and how much solo/editorial return versus private-online coordination should influence the later ordering.
- `empirical trigger`: elevate `queue / capacity honesty` when signups exceed real room or operator capacity. Elevate `hosted convenience` when remote-private play becomes common and self-host friction blocks adoption. Elevate `editorial/content` when authored cadence proves itself and featured content clearly improves repeat return.
- `possible later spike candidate`: none required yet. The later-money question is preserved as two live families rather than a spike-sized uncertainty.
- `sensitivity-ready now`: yes for the early support doctrine, the queue-before-priority rule, and the service-threshold line.
- `still not sensitivity-ready`: no for a final later-family ranking, exact supporter benefits, or any roadmap commitment to paid guaranteed participation.

### 3. Host Ecology And Transition Identity

- `settled doctrine`: host ecology is not one simple ladder. `trusted operators`, `official hosted convenience`, and `sanctioned mirrors / collectives` solve different problems and create different identities. Across all live branches, the project should preserve one canonical authoritative bundle and stable browser-first join grammar.
- `preferred but challengeable branch`: `trusted operators running the canonical authoritative bundle` is the primary transition seam. `official hosted convenience` remains a separate live branch worth preserving, while `sanctioned mirrors / collectives` should be treated as a different promoted-host identity family rather than an automatic next rung.
- `unresolved branch`: it remains open whether official hosted convenience ever becomes first-value before later wrappers mature, whether sanctioned mirrors are worth their governance cost at all, and how much host-mode metadata users actually need.
- `empirical trigger`: promote `trusted operators` when non-Logan operators genuinely want to host and can run/update/recover the canonical bundle without maintainer intervention. Promote `official hosted convenience` when room-start reliability, host availability, or always-on remote access become the main pain. Promote `sanctioned mirrors / collectives` only if the project is willing to publish and enforce standards, contactability, compatibility/version discipline, backup/recovery posture, and review capacity.
- `possible later spike candidate`: `promoted multi-host ecology` centered on sanctioned mirrors / collectives. This is the clearest later spike candidate because it is high-burden, identity-shifting, and still only conditionally justified.
- `sensitivity-ready now`: yes for the family split, the trusted-operator-first carry-forward, and the requirement to keep host-mode labeling and support boundaries explicit.
- `still not sensitivity-ready`: no for any final ranking between `official hosted convenience` and `sanctioned mirrors / collectives`, and no for policy-level detail such as trust contracts or formal host agreements.

### 4. Contribution And Discovery Posture

- `settled doctrine`: open marketplace/public publishing stays deferred. Contribution posture and discovery posture cannot be separated. `unlisted/share-by-link` can arrive earlier than searchable community discovery, and third-party discovery must never silently share the same support or endorsement language as official surfaces.
- `preferred but challengeable branch`: keep `official curated packs` as the main trust surface, preserve `trusted-private sharing / import` as the first non-internal seam, and preserve `invited / partner authors with editorial activation` as the main later middle-space branch.
- `unresolved branch`: it remains open whether later approved outside packs should appear as partner brands or as Prix-curated copies, whether `reviewed submissions` ever become worth the queue/removal burden, and whether `directory-listed but unsupported` belongs inside the core product or only in advanced/self-host channels.
- `empirical trigger`: promote `trusted-private sharing / import` when pack schema, import validation, origin/version display, and private/unlisted labeling are stable. Promote `partner activation` when preview/playtest workflow, rights provenance, metadata, activation, and retirement controls exist. Promote `reviewed submissions` only when reviewer ownership, response-time honesty, rejection/removal posture, and calibration signals exist.
- `possible later spike candidate`: `directory-listed but unsupported additions` for advanced/self-host operators. It is a real later branch, but only if official, partner, and unsupported surfaces can be separated brutally clearly.
- `sensitivity-ready now`: yes for the deferral of open publishing, the early `official + trusted-private` posture, and the later `partner-activated` seam.
- `still not sensitivity-ready`: no for a broader reviewed-submissions program, a searchable third-party catalog, or creator-economy design.

### 5. Content Supply And First Repeat-Return Loop

- `settled doctrine`: the base content engine is `curated evergreen library growth with calibration`. The first product-controlled repeat-return loop is `session recap/review -> private mastery return -> next trusted session`. `room folklore` remains the first emotional recurrence layer, but not the full system loop. `editorial spotlight` is a later prompt layer, and `event carry-over` belongs to its own later memory layer rather than the core mastery ledger.
- `preferred but challengeable branch`: build replay/review as bridge infrastructure, not as a dead-end summary screen, and preserve a bounded editorial spotlight plus a trusted-private contribution seam without letting either become the hidden base answer.
- `unresolved branch`: it remains open which first mastery metric should ship, what the first editorial rhythm should be, how explicit room/group-memory UI must become early, and what the first event-memory surface should look like.
- `empirical trigger`: elevate `editorial spotlight` when the evergreen library is large enough that resurfacing feels like value instead of camouflage for scarcity. Elevate heavier room/group memory when recurring groups become common enough that recap/rematch no longer carries the full social-memory load. Elevate event carry-over only when there is a clear event object and recap surface that can stay separate from mastery history.
- `possible later spike candidate`: `event-memory surface` only if the wrapper-shell lane later proves that bounded event shells matter enough to justify a distinct persistent layer.
- `sensitivity-ready now`: yes for the evergreen-library base, the review-backed-mastery loop, the room-folklore limit, and the memory-layer split between mastery, room recap, event board, and pack/library state.
- `still not sensitivity-ready`: no for the first mastery metric, exact cadence taxonomy, or a final event-memory/UI commitment.

## What Can Close Now

- `GCO-10` can close with this artifact. The project now has one mature-product synthesis that distinguishes settled doctrine from provisional branches and unresolved questions.
- The following can now be treated as closure-grade carry-forward for sensitivity:
  - no universal first post-private wrapper
  - low-burden post-private split between `showcase aftermath` and `share-by-link / challenge`
  - `support-only` early posture plus queue/capacity honesty before monetized priority
  - `trusted operators` as the primary transition hosting seam
  - `official curated library + trusted-private sharing` as the early contribution posture
  - `curated evergreen library + review-backed mastery` as the first content/return stack
- The following can now be treated as explicit guardrails rather than soft intuitions:
  - audience rights as capability bundles
  - `ambient community layer` as a truly later, service-bearing branch
  - `dependable paid participation` as the service-posture threshold
  - `sanctioned mirrors / collectives` as a different host-identity family, not a simple rung
  - searchable discovery as a support/endorsement change, not a neutral visibility tweak
  - event memory as distinct from mastery history

## What Must Stay Open

- one universal first-wrapper ranking
- the later winner between `hosted convenience` and `editorial/content`
- whether `sanctioned mirrors / collectives` are ever worth the governance cost
- whether `reviewed submissions` or `directory-listed but unsupported` should ever become more than narrow later options
- the exact first mastery metric, editorial cadence, audience bundle, and event-memory surface

## Sensitivity Readiness

- `now sensitivity-ready`:
  - test whether canon and Phase 01 steering preserve the newly explicit doctrine above
  - test whether current source-of-truth docs still blur wrapper families, memory layers, host identities, or support thresholds
  - test whether any canon patch would accidentally turn provisional branches into doctrine
- `still not sensitivity-ready`:
  - sensitivity must not force resolution of the still-open rankings just to make the docs feel cleaner
  - sensitivity must not treat preferred-but-challengeable branches as if they were already roadmap commitments
  - sensitivity must not read deferred branches such as open discovery, public marketplace, or paid guaranteed access as quietly reintroduced

## Reconciliation Verdict

- The remediation bundle now has enough closure to support the dedicated post-closure sensitivity pass.
- The main reconciliation outcome is:
  - doctrine is now sufficiently explicit
  - preferred branches are now named as provisional rather than smuggled in
  - unresolved branches are narrower and trigger-bound rather than vague
- In practical terms:
  - the bundle is now `sensitivity-ready in a bounded way`
  - it is `not roadmap-locked in a global way`
- That is the right maturity level for this stage. The synthesis should now be used to drive the next sensitivity pass, not to pretend that every later branch has already been ranked.
