# 05 Remediation Packet A: Wrapper Sequencing And Audience Rights Output

## Packet framing

- Mode: `synthesis`
- Classification: `initial architecture research/planning`
- Question: After trusted private rooms, which wrapper families actually create first value, how should audience rights be decomposed, and what should and should not count as a later `ambient community layer`?
- Scope:
  - compare `showcase aftermath`, `share-by-link / challenge`, `bounded live audience`, `mixed spectator-participant shells`, and `ambient community layer`

Why these belong together:

## What is already settled

Inherited doctrine, not reopened here:

- private-first play remains the product center; later public-light or spectator shells wrap that center rather than replace it
- the product is `substrate plus wrappers`, not one frozen room shape
- visibility is staged: trusted private rooms, then unlisted/share-by-link surfaces, then selective showcase or spectator surfaces, then broader public discovery only with deliberate obligation acceptance
- room, event container, active game instance, and memory layers should remain distinct
- archetypes are load-bearing: couch / recurring private group, private online sync, solo ritual, and bounded event shell are different goods with different burden profiles
- publicness is an obligation change, not merely a traffic increase
- broader public participation, moderation-heavy public services, and ambient public identity remain deferred

## Path of inquiry

- Entry point:
  - the remediation task spec and the specific `GCO-*` gaps above
- Branches considered:
  - results/recap surfaces
  - share-by-link or frozen-challenge surfaces
  - live audience/event shells
  - mixed spectator-participant rights
  - persistent server/community layers
- Branches pursued:
  - `GeoGuessr` for challenge links, result views, live private-party challenge flows, and public-light challenge competition
  - `Kahoot` for explicit split between live host-screen sessions and self-paced assignment links, plus join-security controls
  - `Jackbox` for host-screen audience shells, audience-right variation, and live moderation controls
  - `Discord Stage Channels` for explicit moderator / speaker / audience rights and the public-event burden step-up
  - `Mastodon` for what a real persistent, discoverable community layer demands once it becomes an actual public service
- Branches deferred or abandoned:
  - broad streamer-platform examples because they were weaker on rights granularity than Jackbox + Discord
  - large open creator-platform examples because they would over-index this packet toward publishing and discovery
  - deeper host-topology references because this packet is about wrappers and rights, not host-ecology ordering
- Dead ends:
  - broad spectator-platform search produced more promotion or growth language than actionable role/control detail
- Reframing:
  - the useful comparison is not `private vs community`
  - the useful comparison is `read-after`, `play-later`, `watch-live`, `influence-live`, and `persistent public service`

## Negative-case / failure evidence note

Direct external grounding:

- Jackbox's stream-safety guidance is built around troll avoidance and moderator controls:
  - `Require Twitch` ties players to identities moderators can ban
  - room-code hiding exists so hosts can reveal codes only to trusted audiences
  - VIP/manual censoring exists because user submissions can go bad live
  - limiting player count is recommended to keep outsiders out
- Kahoot's live-join security guidance exists because PIN sharing, bots, and fake participants are normal enough to warrant:
  - 2-step join
  - locking joining
  - nickname generators and filters
  - removing suspicious participants from the lobby
  - not sharing sensitive games publicly
- GeoGuessr exposes moderation even for bounded/private flows:
  - kick during live challenge
  - ban from private party
  - remove challenge leaderboard entries
  - report players from replay or profile
- Discord's Stage guidance says public stages require moderator teams and that making a stage public temporarily makes the server public
- Mastodon treats public server promotion as contingent on moderation, daily backups, multiple people with emergency access, and shutdown notice

Inference:

- `low burden` is not `no burden`
- even bounded or invite-based shells pick up reporting, identity, code/URL control, and removal needs faster than a pure private-room core
- the relevant negative evidence in this packet is not `these shells never work`
- the relevant negative evidence is `products repeatedly added controls because these shells create predictable operator pain and abuse boundaries`

## Live alternatives

### 1. Showcase aftermath

Direct external grounding:

- GeoGuessr's custom challenge flow allows a public leaderboard and nickname anonymization
- GeoGuessr challenge results have a dedicated results view and let the creator remove entries from that leaderboard
- GeoGuessr Live Challenge shows leaderboard state during the round and player progress after the round
- Kahoot's sharing and reporting surface keeps live and assigned results/report flows separate, and public or unlisted content can be link-shared while private content cannot

Inference:

- `showcase aftermath` is a real shell family, not a cosmetic sub-feature
- it is primarily a `read-after` surface:
  - recap
  - standings
  - rivalry trace
  - featured result
  - progress/review
- it can create memory and social spillover without requiring live co-presence or open participant rights
- it still needs privacy and cleanup controls because names, rankings, and bad entries persist longer than a live moment

### 2. Share-by-link / challenge

Direct external grounding:

- GeoGuessr's `Play with Friends` explicitly separates private lobbies from link-share challenge play
- GeoGuessr challenges can be locked to `Only Invited` and then invited by user ID
- Kahoot assignments are explicitly self-paced, not live-presented, and are shared through PIN, link, or QR with no participant account required
- Kahoot assignments are described as less bandwidth-dependent than live games and allow participants to resume later
- GeoGuessr's Daily Challenge shows that a challenge surface can scale to public-light competition without becoming a full community platform

Inference:

- `share-by-link / challenge` is distinct from `showcase aftermath`
- it is primarily a `play-later` surface, not a `read-after` surface
- this branch is especially strong where time-shifted participation matters:
  - solo ritual
  - private online sync across schedules
  - lower-pressure sharing outside a live hosted room
- it can be bounded or public-light depending on who receives the link and whether it attaches to an official daily/programmed cadence

### 3. Bounded live audience

Direct external grounding:

- Jackbox's public-remote-play guidance explicitly points hosts toward Twitch or YouTube for letting people watch, join, and play along
- Jackbox maintains fixed player counts but notes that most games support `Audience`
- Discord Stage Channels default viewers into a muted audience role and require moderator or speaker permissions for live speaking
- Discord documents audience size limits, request-to-speak flows, and moderator powers to move people back to audience
- Kahoot's remote/live guidance explicitly uses a host screen, shared screen, and public live-streaming for large audiences

Inference:

- `bounded live audience` is a real wrapper family, distinct from both `challenge link` and `ambient community`
- it is the first credible `live public-adjacent` shell family
- it is strongest when the product is already behaving like a hosted event, appointment, or show
- it is not automatically the universal first wrapper after private rooms, because its value depends much more on event energy and host authority than aftermath/challenge surfaces do

### 4. Mixed spectator-participant shells

Direct external grounding:

- Jackbox's audience matrix shows materially different audience-right bundles:
  - vote on player submissions
  - award likes
  - submit text
  - answer trivia in parallel
  - predict outcomes
  - influence polls
  - join a team or receive audience ranking
- Discord Stages let audience members request promotion to speaker, while moderators can accept, deny, or demote them back to audience
- Kahoot team modes show additional mixed-device and team-discussion variants inside a host-led shell rather than only one universal participant shape

Inference:

- `audience rights` are not one ladder
- they are a capability menu that can be combined differently by shell:
  - read
  - watch
  - react
  - vote
  - predict
  - submit constrained input
  - request promotion
  - partial play-along
- the right carry-forward is not `add audience later`
- the right carry-forward is `decide which capability bundle belongs to which shell`

### 5. Ambient community layer

Direct external grounding:

- Mastodon explicitly distinguishes:
  - personal one-person operation
  - invite-only family/friends community
  - public server anyone can sign up on
- Mastodon says public internet service brings moderation and community-management work, and that those burdens rise with growth
- the Server Covenant ties public listing to active moderation, daily backups, another person with emergency infrastructure access, and shutdown notice
- the Covenant introduction explains that they moved away from listing every server because automated listing without quality control was not acceptable
- Discord's public-stage guidance shows the same step-up in miniature: making the stage public also makes the server public while the event is live

Inference:

- `ambient community layer` should mean a persistent, discoverable, service-bearing community surface
- it should not mean:
  - recap pages
  - challenge links
  - event-bounded audience shells
  - selective showcase artifacts
- if Prix Guesser keeps this phrase, it should signal a later branch that accepts stronger identity, continuity, moderation, and operations obligations

## Findings

### 1. There is no single universal first post-private wrapper

Direct external grounding:

- GeoGuessr and Kahoot both separate `play later from a link` from `live hosted session`
- GeoGuessr and Kahoot also keep `results/review/share` separate from both
- Jackbox and Discord keep `live audience` distinct from both `active player` and `persistent community`

Inference:

- the current question should not be forced into one global ranking such as `showcase first` or `live audience first`
- the strongest externally grounded answer is `different wrapper families solve different jobs`

### 2. `Showcase aftermath` and `share-by-link / challenge` should stay separate in later synthesis

Direct external grounding:

- GeoGuessr separates challenge creation from result moderation
- Kahoot separates live hosting, assignment, and content sharing/reporting

Inference:

- `showcase aftermath` is a memory/read surface
- `share-by-link / challenge` is an active replay or deferred-participation surface
- they can arrive in either order depending on which archetype is being served first

### 3. `Bounded live audience` is the first credible live public-adjacent shell, but not the first shell for every archetype

Direct external grounding:

- Jackbox and Discord both show a robust audience shell around a host-led core
- both also show visible moderation and code/identity control requirements

Inference:

- if the product wants a `first live audience shell`, this is the right family
- if the product wants a `first post-private wrapper overall`, the answer remains archetype-sensitive

### 4. Audience rights should be modeled as capability bundles, not one ladder

Direct external grounding:

- Jackbox documents materially different audience behaviors by game
- Discord separates audience, speaker, and moderator, with request-to-speak as an explicit promotion action

Inference:

The packet can now justify at least these distinct audience-right classes:

- `read / recap`
- `play later from link`
- `watch live, silent`
- `react / vote / predict`
- `submit constrained audience input`
- `request promotion / speak`
- `full player role`

### 5. `Ambient community layer` should be reserved for a later, heavier branch

Direct external grounding:

- Mastodon's public-facing operator requirements are meaningfully heavier than anything in the recap/challenge/event family
- Discord public-stage guidance shows that even temporary publicness changes accountability

Inference:

- later synthesis should stop using `ambient community layer` as a catch-all final rung
- it should mean a persistent public-service branch only if the project actually intends that branch to stay alive

## First-value vs later-value

| Wrapper family | First-value | Later-value | Preserve-without-prioritizing | Why |
| --- | --- | --- | --- | --- |
| `Showcase aftermath` | high | high | no | immediate room/group memory and low-obligation spillover |
| `Share-by-link / challenge` | high | high | no | strongest time-shifted participation path and strongest solo/private-online extension |
| `Bounded live audience` | medium overall, high for event shell | high | no | strongest eventized public-light shell, but depends on host energy and moderation posture |
| `Mixed spectator-participant shell` | low overall, medium inside event shell | medium-high | yes | useful only once a live audience shell already exists |
| `Ambient community layer` | low | possible high, but conditional | yes | real later branch only if the project accepts persistent public-service obligations |

Important split:

- `first-value` is about what extends the private-first center with the least mismatch
- `later-value` is about which branch might matter if the product becomes more public, more recurring, or more service-bearing
- a branch can have strong later-value without being the right first move

## Archetype-to-burden translation

| Archetype | Strongest first wrapper candidates | Main value created | Main new burden | Carry-forward caution |
| --- | --- | --- | --- | --- |
| `couch / recurring private group` | `showcase aftermath`, then `share-by-link / challenge` | room folklore, rivalry traces, replay invitations, low-friction sharing between sessions | naming/privacy cleanup, lightweight reporting, expectation that results persist | do not over-rotate into live public audience if the real good is house memory |
| `private online sync` | `share-by-link / challenge`, then `showcase aftermath` | handles scheduling mismatch, lets a trusted group keep competing across time, preserves recap value after live sessions | invite/link control, results privacy, possible confusion between `replay later` and `live room` | do not assume event-style spectatorship is the first need here |
| `solo ritual` | `share-by-link / challenge`, `daily/programmed challenge`, selective `showcase aftermath` | strongest cadence extension, personal mastery, public-light comparison without heavy social infrastructure | content cadence, leaderboard hygiene, status/visibility clarity | solo value can grow without any ambient community layer |
| `bounded event shell` | `bounded live audience`, then `mixed spectator-participant shell`, with `showcase aftermath` as support | appointment energy, hostable reveal, readable audience shell, event recap afterward | moderator presence, join gating, code safety, stronger operator responsibility | this is where live audience is first; do not universalize that answer to the other archetypes |

## Trigger conditions

Promote `showcase aftermath` if:

- groups naturally revisit standings, rivalries, or notable reveals after sessions
- users already share screenshots or ad hoc recaps outside the product
- room/group/event memory looks like the first repeat-return layer

Promote `share-by-link / challenge` if:

- time-shifted play matters more than live watching
- solo ritual or private-online sync is the clearer early extension
- hosts want to challenge absent friends without scheduling another session
- content cadence can support recurring challenges

Promote `bounded live audience` if:

- there is repeated demand for hosted nights, event wrappers, or readable spectator moments
- hosts can reliably manage audience access and moderation
- the product has enough reveal clarity that watching is valuable even without active play

Promote `mixed spectator-participant shell` if:

- passive viewing proves too thin once live audience exists
- there is a concrete event use for vote/react/predict/request-to-speak rights
- the host/moderation posture can absorb those extra capabilities

Promote `ambient community layer` only if:

- the project is willing to accept persistent moderation work
- backup/recovery and shutdown posture become real product promises
- more than one person can cover operational continuity
- discoverability, identity, and public-service language are deliberate rather than accidental

## Recommended carry-forward

Main verdict:

- do not carry forward one universal `first post-private wrapper`
- carry forward a split answer:
  - `showcase aftermath` and `share-by-link / challenge` are the two strongest low-burden post-private branches
  - `bounded live audience` is the first credible live public-adjacent shell, especially for the bounded-event archetype
  - `ambient community layer` is distinctly later and should no longer be used as a vague bucket

Recommended carry-forward statements for later synthesis:

- treat `showcase aftermath` and `share-by-link / challenge` as separate branch families
- treat `bounded live audience` as an archetype-indexed answer, not a global first answer
- model audience rights as capability bundles, not a single ladder
- reserve `ambient community layer` for persistent, discoverable, moderation-bearing community service
- if later synthesis still wants one first wrapper, it must say which archetype it is optimizing for and which others it is not optimizing first

## Explicit deferrals

- exact roadmap ordering between `showcase aftermath` and `share-by-link / challenge`
- exact feature set inside mixed spectator-participant shells
- exact moderation tooling or governance for public-facing shells
- exact persistent-identity model for recap/challenge surfaces
- open public discovery, stranger participation, or public room browsing
- final content-flywheel implications
- support/pricing/hosting posture

## What should remain open

- whether the first non-private extension should optimize for room/group memory or for time-shifted replay
- whether a daily/programmed challenge belongs in the same branch family as friend-to-friend challenge links or should be treated as a later editorial step
- how much `showcase aftermath` should be read-only versus lightly interactive
- which audience-right bundles are worth supporting first inside a bounded event shell
- whether any live audience shell is earned before stronger solo/async reuse is proven

## What later converged synthesis must reconcile

- wrapper sequencing with the still-open recurrence question:
  - is the first repeat-return loop room folklore, solo ritual, editorial challenge, or event cadence?
- wrapper sequencing with memory-layer translation:
  - room/group memory
  - player memory
  - event memory
  - content/history memory
- wrapper sequencing with promise grammar:
  - which shells stay low-obligation and which imply stronger support/moderation promises
- wrapper sequencing with host-ecology work:
  - bounded live audience and persistent community are not the same obligation step
- wrapper sequencing with archetype priority:
  - if one branch is chosen first, later synthesis must state which archetypes are being intentionally served first and which are being preserved rather than prioritized
